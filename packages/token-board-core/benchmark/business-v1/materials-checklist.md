# 正式评测前的材料准备

本题库目前完成了会话调研、12 道题面和验收规范。这里列出把题目变成可重复运行的评测所需的准备步骤。清单尚未执行，不能把题面校验通过写成模型通过了业务测试。

## 固定任务起点

每题记录起始源码或文档的文件清单、内容哈希、依赖锁及环境版本。真实工作区有未提交修改时，在独立副本中构建材料，不用当前 HEAD 代替用户当时的状态，不重置用户工作区。

如果无法找回故障前材料，采用明确标注的重建场景。保留完整工作链路和原始约束，不把跨层故障缩成一个与业务脱节的算法函数。历史解决方案只能用于评审侧验证，不能放进参评 Agent 的输入。

文档保护题需要分别冻结 Git 旧版、用户手动保存版、当前损坏版和参考材料。架构题需要冻结两个源码版本及固定的更新时机。性能题需要独立的语义对照、固定合成数据、资源限制和负载，不能用待测实现自己生成全部预期结果。

## 隔离模型输入和评审材料

参评 Agent 只接收 `prompts/Bxx.txt` 与该题材料清单中标为可见的起始文件。不要把整个 `business-v1` 目录、会话日志、当前完整仓库历史或已修复版本挂载给它。

评审规范、预期结果、历史工具输出和本地私有来源索引由外部评测进程保存。在参评 Agent 停止后再运行隐藏验收，记录完整产物和操作轨迹。临时目录本身不提供文件访问隔离，需要独立用户、容器或其他实际可验证的边界。

涉及登录、部署、手机控制的题目使用测试 Profile、本地服务和设备模拟器。历史会话中的生产授权不自动适用于未来评测；评测题面中的操作授权只覆盖明确列出的测试环境。

## 先验证题目本身

故障修复题应确认起始状态能复现症状、参考修复通过全部关键验收，而且另一个不同但正确的实现也不会因写法不同被误判。开放创作题应确认评分锚点和用户选择脚本可执行，不要求空白起点通过或失败某段代码测试。

检查材料和说明没有透露历史根因。对可能失败的外部服务，预先定义基础设施失败与模型失败的分界。缺数据库、缺设备或未启动浏览器导致的跳过不得当成验收通过。

人工选择、澄清回答和中途源码更新需在两组模型的相同阶段按相同脚本提供。Agent 已正确完成时，不额外制造一次错误来触发恢复分支；恢复能力使用单独的损坏起点测量，并沿用同一事故族权重。

## 冻结结果口径

按 `evaluation-protocol.md` 记录版本、预算、关键验收、人工介入和全部运行结果。性能门槛在参评之前按固定环境确定，不能照抄历史机器上一次观测的耗时。

当前 `suite.json` 的 `replayReady` 为 `false`。只有材料已打包、隔离已验证、评分器与参考结果已检查，才可建立新的可运行版本并更新状态。本目录不直接交给旧版 `tools/eval-runner/run.mjs`。
