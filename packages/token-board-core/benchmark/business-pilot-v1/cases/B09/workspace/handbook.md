## 二、云杉科技·流舟实习

## 1. ProfilePilot：真实 Chrome 与 Agent 的浏览器控制面

### 一句话定位

解决真实登录态安全复用与多 Agent 并发调度冲突的 local-first Chrome Profile 控制台与受控 CDP 网关。

### 30 秒版

我在流舟实习期间主导研发了 ProfilePilot。我们调研评测了市面上 5 款主流浏览器自动化工具，发现它们都无法解决“人与 Agent 抢占同一个 Chrome 窗口与焦点”的痛点。ProfilePilot 采用双核架构：右翼是 Profile 数据管理面，通过 `diff → staging → rename → backup/rollback` 事务化同步真实 Chrome 登录态到隔离副本，规避 Chrome 136+ 限制远程调试端口的安全约束；左翼是 Agent 协同控制面，通过本地 Gateway 集中管理 Profile 租约与代次（`controlGeneration`），为 CDP 连接派发一次性 Ticket；结合页面悬浮控制条与 macOS 原生 Input Guard，实现随时人机接管且互不抢占。日常稳定支撑并行运行 2 个独立 Agent 浏览器 Session，赋能商业化多需求并发自测。

### 90 秒展开版

**业务背景与痛点**：在流舟商业化拦截和复杂配置流验证中，大量场景必须由 Agent 在真实内网登录态下操作页面闭环验证，而支付与高危环节又需人工随时介入。传统方案面临三大死穴：第一，使用纯净临时浏览器需要反复重新登录公司内网多套系统；第二，直接给日常默认 Chrome 挂 `--remote-debugging-port`，不仅存在严重的数据污染隐患，且 Chrome 136 之后已对默认数据目录限制远程调试；第三，多个 Agent 或人和 Agent 同时操作时，窗口焦点抢占、点击冲突频发，甚至造成误触线上数据的灾难性后果。

**双核架构设计**：

1. **右翼：本机优先 Profile 数据管理面**：从 Chrome `Local State` 和系统进程中智能发现真实 Profile，并在独立 `user-data-dir` 中创建隔离副本。为了防止活跃浏览器写入造成数据损坏，我设计了事务同步状态机：先做差异预览，把 Cookies、Storage 写入 staging 暂存区，完成后使用原子 rename 快速切换；覆盖前自动创建备份，遇到异常或进程崩溃可瞬间回滚。
2. **左翼：可编程 Agent 协同控制面**：彻底告别裸连 CDP 端口。前端 Wrapper 解析指令向 Gateway 申领短时一次性 Ticket，Daemon 通过 WebSocket 建连，CDP 指令经 Gateway 进行安全审计和请求拦截后，通过专用 pipe 转发给浏览器。Gateway 实行严格的“一 Profile 一 Session”排他租约调度，并通过代次计数器（`controlGeneration`）进行权限管理——当用户接管、任务归还或任务重置时，Gateway 立即递增代次，旧 WebSocket 连接的发送权限瞬间失效，杜绝幽灵指令。
3. **可见可接管的人机分层防护**：在页面端注入轻量悬浮控制条（可见任务状态、随时暂停/接管/恢复）；同时清醒认识到 DOM 遮罩防不住浏览器原生标签栏和地址栏，因此在 macOS 端增加了按 Chrome 进程拦截的原生 Input Guard，结合 Gateway 所有权仲裁，构建了从网页 UI、系统输入层到协议通信层的三重防护壁垒。

### 最值得展开的技术点

- **登录态事务级同步语义**：`diff → staging → rename → backup/rollback`，保障数据无损、可取消、可崩溃恢复。
- **Gateway 租约与代次协议**：Profile Lease 解决并发归属，一次性 Ticket 验证连接身份，`controlGeneration` 彻底斩断旧连接越权。
- **三层人机协同防护体系**：网页 DOM 悬浮条（交互感知） + 原生 Input Guard（真实系统输入拦截） + Gateway（连接所有权终审）。
- **多需求并发自测落地**：日常并行运行 2 个独立 Agent 浏览器 Session，实现研发多分支多需求并行验证。

### 常见追问

**为什么市面已有 Playwright、Puppeteer，还要自研 ProfilePilot？**

市面工具面向自动化爬虫或端到端测试，默认假定独占纯净浏览器。我们评测 5 款主流工具后确认：没有工具能解决“人和 Agent 共用浏览器时的焦点抢占与接管”；也没有工具能无感、安全地将真实 Chrome 登录态事务化同步到隔离环境以绕过 Chrome 136 端口限制。ProfilePilot 解决的是 AI 辅助真实研发验证的控制面空白。

**为什么给 Chrome 开一个固定 CDP 端口还不够？**

固定端口只能建立网络连接，回答不了高层协同问题：“现在是哪个 Agent 在操作？”“用户点击接管后，Agent 发送的下一个 CDP 包如何拒收？” Gateway 将端口映射、Session 租约、Ticket 凭证和控制代次统一收口，才能在协议层实现强约束。

**登录态同步的原子性和备份机制具体是怎么做的？**

真实 Chrome 运行时会锁住 Cookies 数据库文件。直接复制可能拷出残缺数据。我们是在冷启动或静默期读取只读快照，先拷到 staging 临时目录完成结构校验，再触发 rename 原子替换当前隔离 Profile 的对应路径；同时保留最近一次 snapshot 备份，出现校验异常直接重命名恢复。

**DOM 遮罩和原生 Input Guard 的边界是什么？**

DOM 遮罩仅能在视口内防误触，无法拦截用户点击标签页切换、关闭窗口、地址栏跳转或原生 dialog；macOS 下借助系统 Accessibility/Event Tap 实现进程级 Input Guard，在接管前拦截鼠标键盘发往 Chrome 进程的真实物理事件，把防误触做到系统级。

**跨平台支持现状怎么说最准确？**

Profile 管理、事务同步与 Gateway 核心控制协议跨平台完全支持（macOS / Windows）；原生 Input Guard 和窗口焦点保护在 macOS 上实现最为完整，Windows 上部分底层能力仍处于受限支持状态。

## 2. FlowDesk 测试账号切换工具链

### 一句话定位

服务团队 10+ 人的高频提效基座，通过三代演进实现从 3 分钟人工切号到 12 秒内安全注入，兼顾人和 Agent 双入口。

### 30 秒版

在 FlowDesk 商业化开发中，需要在个人免费/进阶/旗舰、企业版及不同额度账号间高频切换，人工流程单次超过 3 分钟。我设计并建设了测试账号切换工具链，历经三代演进：第一代 Playwright 模拟点击易脆且慢；第二代接口调用遭遇反爬动态签名与短信验证；第三代通过内网服务直接以目标 UID 换取合法 Session 并注入当前环境，切回本人走团队协作平台 SSO `prompt=none` 静默授权。工具链通过企业云与 AccessGate 实现双重权限管控，提供 Chrome 扩展（面向人工）与 CLI（面向 Agent）双入口，将切号耗时缩短至 12 秒以内，日常服务组内 10+ 同学。

### 90 秒展开版

**业务痛点与复杂度**：商业化开发需要验证复杂的套餐权限、企业成员与额度边界。人工流程需要先在团队协作平台表格里筛选可用账号、在 FlowDesk 退出当前登录、输入账密登录、切换到指定企业组织，再核对套餐和剩余额度是否满足测试要求，单次操作至少 3 分钟。更痛苦的是，苹果内购、CRM 订阅等特定渠道账号构造复杂，且很多账号是一次性的（状态改变后无法复原测试），开发和联调效率极其低下。

**三代方案演进**：

1. **第一代（Playwright UI 模拟点击）**：写脚本自动填表单、点登录按钮。在真实业务中极度脆弱：前端改个 DOM class 脚本就挂，耗时仍在 20~30 秒，遇到滑块或验证码直接彻底中断。
2. **第二代（纯接口调用登出/登录）**：绕过 UI 直接调 Passport 登录接口。但遭遇了双重阻碍：一是字节内网风控与反爬的动态签名拦截；二是许多企业主账号强制绑定了手机号二次短信验证或 MFA，接口无法自动化闭环。
3. **第三代（UID 换取 Session Cookie 替换 + 团队协作平台静默授权）**：彻底跳出“模拟用户输入账密”的思维定式。在服务端搭建专有换号服务，直接使用目标测试账号的 UID 换取合法的临时 Session 凭证，前端通过 Chrome 扩展的 Cookies API 或 CLI 直接注入当前环境，秒级完成身份切换；当需要切回本人账号时，绝不在本地明文缓存个人 Cookie，而是打开一个带有 `prompt=none` 参数的静默跳转 Tab，无感复用企业团队协作平台 SSO 的最新登录态重新换取 Session。

**双入口与安全合规**：

- **双端形态设计**：Chrome 扩展提供 Popup 界面，适合人工开发者按套餐、企业角色可视化筛选与一键切号；CLI 专为 Agent 打造，支持绑定指定 Tab、输出机器可读的标准 JSON 错误码，并与 ProfilePilot 协同编排。
- **全链路安全防护**：换号服务部署在内网企业云环境，调用端接入 AccessGate 权限系统进行双重鉴权；账号凭据与 Session 不落持久化存储，操作日志全程审计，杜绝敏感登录态泄露。

### 最值得展开的技术点

- **跳出模拟账密的第三代架构**：从 UI 模拟（1代）到接口模拟（2代），最终演进为服务端 UID 签发 Session Cookie 直接注入（3代），本质是把不可靠的外部行为变成可控的内部状态迁移。
- **切回本人的静默授权（`prompt=none`）**：安全合规的最佳实践——避免持久化个人敏感 Cookie，利用标准 OIDC/SSO 协议的静默模式秒级重获本人有效身份。
- **双重身份安全鉴权（企业云 + AccessGate）**：防止提效工具沦为提权后门，严格保证内网测试账号与生产环境的隔离边界。
- **人机双入口协同**：扩展负责高可用交互与异常人机 fallback，CLI 负责确定性编排与 Agent 集成。

### 常见追问

**为什么切号工具必须经历三代演进？为什么一开始没直接想到第三代？**

最初直觉是把人的操作自动化（Playwright），但在真实业务场景中，验证码、反爬签名和二次短信验证是自动化模拟无法逾越的鸿沟；第二代虽然加速了链路，但仍受限于账密登录协议。第三代从系统底层视角切入，利用内部特权测试服务的 UID-to-Session 机制，才彻底将流程收敛为确定性的数据写入。

**切回本人账号时，为什么不直接把旧的个人 Cookie 存在 LocalStorage 里备用？**

这是严重的安全违规：个人 Cookie 包含开发者本人的完整内网访问权限，明文落地存储极易被跨站脚本（XSS）窃取或滥用；且 Cookie 存在服务端过期和主动失效机制。利用企业团队协作平台 SSO 的 `prompt=none` 协议重新走一遍无感签发，既绝对安全合规，又保证获取的是最新可用凭证。

**工具从 3 分钟降到 12 秒以内，具体的统计口径是什么？**

3 分钟以上是人工查表、手动登出、重输账密、切企业和核验额度的完整耗时；12 秒以内是指在 Chrome 插件中点击目标账号、服务端换签 Session 并由插件完成本地 Cookie 替换的端到端真实耗时，组内 10+ 研发日常高频依赖。

**如何保证切号后环境的真实有效性？**

注入 Session 后，工具会自动在同一 Origin 下发起三向校验：校验 Passport 当前用户 UID、企业列表里的 `enterprise_id`，以及套餐订阅详情接口返回的 `user_level_v2` 与额度，全部一致才判定成功。
