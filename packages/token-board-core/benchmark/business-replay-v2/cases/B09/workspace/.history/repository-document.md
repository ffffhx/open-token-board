> 这是一份面向 2027 届前端校招的个人项目复盘与口述手册。公开版保留可用于面试表达的技术脉络和数字口径，不包含内部代码、账号、凭据或未公开文档内容。

> 适用场景：2027 届前端开发校招面试。本文是口述稿和追问提纲，不是简历正文。

## 怎么使用这份手册

每个项目都按“背景—问题—我的工作—结果—复盘”组织。面试官只给半分钟时讲“30 秒版”；对方继续追问时，再从“展开版”和“常见追问”中选择一两个点，不要一次把所有细节说完。

回答时尽量坚持三个原则：

1. 先说业务问题，再说技术名词。
2. 明确区分个人产出、团队协作和业务方接入，不把团队结果全部说成个人编码量。
3. 数字后面要带统计口径，例如“900+”是 Git 不识别重命名时的新旧路径数，不是 900 个完全独立的新文件。

我比较突出的特点是 React、TypeScript 和前端工程能力比较扎实，同时深度使用 Claude Code 和 Codex，愿意把团队里的隐性经验沉淀成真正可执行、可验证的 Agent 工具链。我希望继续做复杂前端、工程基础设施或者 AI 与前端结合方向的工作。

## 二、云杉科技·流舟实习

## 1. ProfilePilot：真实 Chrome 与 Agent 的浏览器控制面

### 一句话定位

ProfilePilot 是一个 local-first 的 Chrome Profile 与 Agent 浏览器控制面，解决真实登录态如何安全复用，以及人和多个 Agent 共用浏览器时如何明确控制权的问题。

### 30 秒版

我在流舟实习期间研发了 ProfilePilot。它不是普通的浏览器启动器，而是把真实 Chrome Profile、隔离副本、登录态迁移和 Agent 控制权放到一个本地控制面里。Agent 通过本地 Gateway 使用逻辑 CDP 端口，系统用“一 Profile 一 Session”的租约避免多个 Agent 抢占；用户接管时会吊销旧的控制代次，Agent 等待归还。登录态同步则采用暂存、原子替换和备份回滚，避免把真实浏览器数据复制到一半。项目已经交付 macOS 和 Windows 版本，其中原生输入保护在 macOS 上能力最完整。

### 90 秒展开版

这个项目源于一个很实际的问题：Agent 如果使用干净浏览器，很多内部系统都要重新登录；如果直接使用用户日常 Chrome，又会遇到默认 Profile 无法安全开放 CDP、多个 Agent 抢同一个 Profile，以及用户和 Agent 同时点击造成误操作的问题。

我的方案分成三层。第一层是数据层，从 Chrome 的 `Local State`、Profile 目录和进程状态中发现真实 Profile，并通过独立 `user-data-dir` 创建隔离副本。登录态和扩展迁移不是直接覆盖，而是先做差异预览，把数据复制到 staging，完成后用 rename 做短时切换；覆盖前自动备份，失败可以回滚。

第二层是连接层。我没有让 Agent 直接连裸 CDP 端口，而是在 Chrome 的 debugging pipe 前加本地 Gateway。每个连接都带 Session 身份，一份 Profile 同一时刻只租给一个 Session；Gateway 通过短时一次性 Ticket 和 `controlGeneration` 管理连接，接管、归还或结束任务都会推进代次，所以旧 WebSocket 不能继续发送命令。

第三层是人机协作层。页面 overlay 负责展示 Agent、任务和接管入口，但 DOM 遮罩挡不住标签栏和地址栏，所以 macOS 端又增加了原生 Input Guard，按 Chrome 进程拦截真实点击、拖拽和滚轮；Gateway 才是控制权的最终事实来源。这样就把“看起来被锁住”变成了协议层和系统输入层都真实生效。

### 最值得展开的技术点

- 登录态同步的事务语义：`diff → staging → rename → backup/rollback`，暂停、取消和崩溃恢复都有明确结果。
- Gateway 控制协议：Profile lease 解决并发归属，Ticket 解决连接身份，generation 解决旧连接吊销。
- 人机接管状态机：用户接管时原 Session 仍保留租约，防止其他 Agent 趁人工操作时抢占；只有完成或释放才真正释放 Profile。
- overlay 与 Input Guard 分层：网页层负责沟通，原生层负责真实输入，Gateway 负责所有权。

### 常见追问

**为什么不直接让 Agent 操作默认 Chrome Profile？**

默认 Profile 是用户最重要的登录态和数据边界，直接操作的失败成本太高；而且 Chrome 136 之后默认数据目录会限制远程调试端口。我的方案是把需要的登录态事务化同步到隔离 Profile，再交给 Agent，代价是多一次复制，换来可回滚、可销毁和清晰的身份边界。

**为什么固定 CDP 端口还不够？**

端口只能回答“连到哪个浏览器”，回答不了“哪个 Session 有权操作”“用户接管后旧连接是否失效”。Gateway 把端口映射、Session、租约和控制代次放进同一个协议里，才能形成强约束。

**这个项目最深的坑是什么？**

最初我以为页面遮罩就能防误触，实际它既挡不住浏览器原生 UI，也可能只是视觉层不可点。后来我把问题重新拆成 DOM 展示、原生输入拦截和 Gateway 所有权三层，这是项目里最重要的一次方案纠偏。

**跨平台怎么说才准确？**

Profile 管理、迁移和 Gateway 主链路支持 macOS / Windows；窗口观察和原生 Input Guard 高度依赖系统能力，目前 macOS 最完整，Windows 的部分能力仍是受限或实验状态。

## 2. FlowDesk 测试账号切换工具链

### 一句话定位

把“找账号—退出旧账号—登录—切企业—校验套餐和额度—异常恢复”从人工操作变成扩展、CLI 和 Agent Skill 共用的一条闭环工具链。

### 30 秒版

FlowDesk 商业化测试经常要在个人版、企业版和不同额度账号之间切换，人工流程需要查账号、登录、切企业并再次确认权益，单次通常超过 2 分钟。我建设了 Chrome 扩展、CLI 和 Agent Skill 三种入口：先按企业、套餐、角色和额度筛选账号，再通过 CloudIdentity 与 FlowDesk Passport 完成登录，最后用 UID、enterprise ID、订阅等级和额度做闭环校验。工具在商业化团队内推广后，单次切换降到约 20 秒，同时覆盖额外安全验证、有限重试、限流熔断和团队协作平台 SSO 切回本人账号。

### 90 秒展开版

这个项目的难点不在“自动填一个用户名密码”，而在于 FlowDesk 同时存在个人主账号、企业主账号和企业成员账号，不同账号的 CloudIdentity 登录链路、企业选择和最终权益信号都不一样。只看到页面进入首页并不能证明切对了账号，更不能证明套餐和额度符合测试目标。

我把流程设计成查询、登录、验证和恢复四段。查询阶段通过账号服务按套餐权益、企业角色和动态条件筛选候选账号，并设置最大查询次数，匹配不到就明确失败，不降级到错误账号。登录阶段优先走后台 API：获取 CloudIdentity auth code，再调用 FlowDesk Passport 完成退出和登录；企业成员走独立的 SaaS user login 流程，不能误用个人主账号链路。

验证阶段始终在同一个目标 Origin 下读取 Passport 当前用户、企业列表和订阅详情，综合校验 UID、enterprise ID、`user_level_v2` 与额度。遇到需要短信、MFA 或安全验证的账号，先跳过并尝试下一个候选；只有候选都不可用时才进入人工验证 fallback。

在人和 Agent 两种入口上，我让 Chrome 扩展负责 popup 和人工恢复体验，CLI 负责精确 Tab 复用、ProfilePilot/CDP 编排和机器可读错误，Skill 再把套餐语言映射、验证标准和安全边界提供给 Agent。切回本人账号时不复制 Cookie，而是重新走团队协作平台 SSO，并用本次 SSO 返回的身份指纹做额外校验。

### 最值得展开的技术点

- 登录成功不是终点，最终条件是账号身份、企业、套餐与额度全部匹配。
- 企业成员和个人账号采用不同的 CloudIdentity 流程，避免误登录到主账号。
- 扩展、CLI、Skill 共享业务约束，但浏览器编排各自独立：人用 popup，Agent 用机器可读 CLI。
- 密码只在一次切换中使用，不写入持久存储；Cookie 不打印、不导出，切回本人走真实 SSO。

### 常见追问

**为什么同时做扩展和 CLI？**

扩展适合人直接选择套餐和角色，也适合处理需要人工验证的页面；CLI 更适合 Agent，能精确复用指定 Tab、返回结构化错误并与 ProfilePilot Session 绑定。两者解决的是同一业务问题，但交互和失败语义不同。

**怎么确认真的切成功了？**

个人账号校验 Passport UID，企业账号校验 `enterprise_id`，套餐校验订阅详情里的等级，额度作为强辅助信号；不能只靠昵称或页面出现“首页”判断。

**2 分钟到 20 秒怎么解释？**

2 分钟以上是人工完成查询、退出、登录、企业切换和验证的完整路径；约 20 秒是工具在无需额外 MFA 的可用账号上走完同一闭环的团队实际使用口径。面试时不要把需要人工验证码的异常链路也说成稳定 20 秒。

## 3. 内部 Agent Skills 工具链

### 一句话定位

把团队里依赖内网平台、环境路由和人工经验的研发流程，沉淀为 Agent 能理解、执行、校验和恢复的 Skills。

### 30 秒版

我在流舟团队沉淀了多个内部 Agent Skills，覆盖团队协作平台消息、IssueHub 研发任务、DeployLane/PPE 泳道部署，以及本地、PPE 和线上验证。它们不是简单的命令说明，而是把环境选择、权限确认、失败诊断和验收标准都编码进去。例如一次 FlowDesk 改动可以从 IssueHub dry-run 和建单开始，部署到 DeployLane 泳道，再通过 TrafficBridge 注入真实域名流量，最后由浏览器和流量记录共同证明改动确实命中了目标环境，从而形成研发任务到结果验收的自动化闭环。

### 90 秒展开版

团队里很多流程看起来只是“跑一个命令”，但真正容易出错的是隐性上下文。例如 FlowDesk Space 和 Coding 的端口不同，本地验证必须经过 TrafficBridge 真实域名，PPE 泳道的请求头要根据 channel 配置决定，IssueHub 还涉及工作流模板、目标分支、重复 MR 和部署失败诊断。如果只让通用 Agent 自己猜，很容易出现“页面打开了，但其实没打到本地或泳道”的假验证。

我的做法是把流程拆成 Skill 负责决策和边界、脚本负责确定性执行、官方 CLI 负责平台操作。IssueHub Skill 会动态解析工作区和模板，先 dry-run 审计变更卡，再创建或复用任务；部署后返回泳道和流量头，失败时检查流水线、channel、MR 与目标分支。验证 Skill 则覆盖本地、PPE 和线上三套路径：启动正确的 dev server，核对 TrafficBridge 和 System Proxy，通过真实 Chrome 访问真实域名，最后同时检查页面结果、TrafficBridge traffic 和服务日志。

团队协作平台消息 Skill 也不是直接“随便发”，而是要求精确解析群、人或邮箱，确认发送身份、收件人和内容；没有唯一目标时必须停止。这样 Skill 沉淀的不只是工具用法，还包括安全规则和完成标准。

### 最值得展开的技术点

- Skill、脚本和 CLI 分层：Skill 表达策略与上下文，脚本封装确定流程，`company-cli` / `team-cli` 执行平台能力。
- 防止假验证：页面可访问不等于流量命中目标环境，必须结合真实域名、规则命中和服务日志。
- 失败可诊断：IssueHub 卡点要回读 stage、pipeline、channel 和 MR 状态，不能因超时盲目重复建单。
- 安全边界：外部写操作先确认目标；消息发送必须精确匹配；JWT、Cookie、测试账号密码不进入回复或日志。

### 常见追问

**Skill 和普通脚本有什么区别？**

脚本擅长执行一个输入明确的确定流程；Skill 还要理解用户意图、选择路径、补齐上下文、处理权限和决定什么证据才算完成。两者组合后，Agent 才不会只是“把命令跑完”。

**这类工作为什么有技术价值？**

价值不在写多少 Markdown，而在把过去只存在于个人经验里的环境约束、失败模式和验收标准变成可复用协议，让 Agent 在正确边界内稳定完成端到端任务。

## 4. FlowDesk 商业化域架构重构

### 一句话定位

把散落在多个历史包中的订阅、付费墙和积分能力，治理成有明确领域边界、稳定对外 API 和自动化依赖约束的商业化子域。

### 30 秒版

FlowDesk 商业化代码原来分散在 6 个以上的包里，存在 common 反向依赖 UI 包、业务方深路径引用和跨 feature 网状依赖。我推动把它重组为 `core / shared / feature / entry` 四层、六个物理包：底层放领域逻辑，中间放跨场景 UI 和订阅、付费墙、活动三个 feature，外部业务统一从 entry 白名单出口接入。完整分支覆盖 518 个逻辑变更文件；按 Git 不识别 rename 的新旧路径口径是 904 条，所以简历写 900+ 路径。迁移后清空旧包，并通过 lint 边界、Entry exports、测试迁移和 bundle diff 固化约束，Total JS 只增长 0.47%。

### 90 秒展开版

这次重构的核心问题不是目录不好看，而是依赖方向失控。原来的订阅、付费墙、积分、store 和 setup 分散在多个包中，`subscription-common` 甚至反向依赖付费墙 UI 再导出类型；外部业务还会深路径引用内部实现。结果是一个付费墙改动可能牵连 layout、home、deployment 等很多入口。

我先从真实消费关系出发定义四层。`core` 只放 store、Hook、类型、协议适配等无 UI 的领域基座；`shared` 放被多个 feature 或入口复用的 UI 块，但不能承载完整业务链路；`feature-subscription`、`feature-paywall`、`feature-activity` 保持业务内聚，默认禁止 feature 互相依赖；`entry` 是唯一对外 API 面，只允许显式 subpath export 和轻量编排。

迁移策略不是一次性改完再祈祷能跑，而是先用 entry facade 保住外部契约，再逐步下沉和移动实现，最后清空旧包。完整分支相对 merge-base 有 518 个逻辑变更文件；如果关闭 rename detection，删除旧路径和新增新路径会得到 904 条路径记录。为了避免重构后再次退化，我补了依赖边界 lint、显式 exports、CI 构建和包体积对比，还找回并迁移了旧包删除时遗漏的 21 个单测。最终 Total JS 从 32.19 MB 到 32.40 MB，增幅 0.47%。

### 最值得展开的技术点

- `entry` 不是普通 barrel file，而是对外 API 白名单和跨 feature 轻量编排层。
- feature 需要另一个 feature 时，只有三种处理：纯逻辑下沉 core、复用 UI 抽 shared、组合流程上移 entry。
- 渐进迁移用 facade 稳住调用方，避免同时改内部结构和外部契约。
- 架构约束必须进入 lint、exports、测试和 bundle diff，不能只停留在文档。

### 常见追问

**900+ 文件到底是什么口径？**

完整分支相对 merge-base 是 518 个逻辑变更文件；关闭 Git rename detection 后，旧文件删除与新文件新增分别计数，共 904 条新旧路径。面试时应说“覆盖 900+ 新旧文件路径”，不要说“新写了 900 个文件”。

**为什么需要 entry，直接从各 feature 根出口导入不行吗？**

直接依赖 feature 会让调用方感知内部拆分，也容易把实验性实现变成永久 API。entry 通过显式白名单屏蔽内部变化，还能在不制造 feature-to-feature 依赖的前提下做少量组合。

**AI 很擅长搬文件，这个项目难在哪里？**

机械迁移确实可以由 AI 加速，真正困难的是从真实消费关系定义边界、保住外部契约、处理 rebase 后新增残留、找回测试、修正 CI 依赖声明，并用规则防止新结构再次退化。我的价值主要体现在这些判断和验收闭环。

## 5. 流舟 3.0 企业权益与付费墙

### 一句话定位

把不同业务各自实现的套餐判断、额度判断和升级引导，抽象成统一权益判断模型和可复用付费墙接入链路。

### 30 秒版

流舟 3.0 同时上线多人协作、自定义模型和 Agent、云设备增购与扩容等商业化能力。过去业务方容易各自读取权益字段并写判断，口径不一致。我负责设计统一的权益判断 Hook、纯函数 evaluator 和类型化场景上下文，首期覆盖 14 类业务场景，统一处理禁止、无限和限额三种策略；同时提供“下一个可用套餐”能力，并把判断结果接入团队沉淀的公共付费墙 UI。最后推动相关业务方按同一规范完成接入。

### 90 秒展开版

这项工作的背景是流舟 3.0 有多条业务线同时接商业化：多人协作要判断套餐是否支持以及新增后是否超额；自定义模型和 Agent 有能力开关；云手机、云电脑、Sandbox 和 SandboxHub 同时涉及能否使用、最大规格和数量上限。如果每个业务直接读取后端权益结构，很快就会出现字段理解、默认策略和升级目标不一致。

我的方案把“获取原始权益”和“根据业务动作做判断”拆开。底层把后端 counter 统一解释为 `Forbidden / Unlimited / Limited`；业务方通过类型化 context 只传当前数量、本次新增数量或目标 CPU 规格，`evaluateBenefit` 作为纯函数计算可用性和原因，React 侧的 `useBenefitCheck` 负责订阅权益 store。纯函数还可以给 App 或非 React 场景复用，也便于单测。

另一个关键能力是 `useNextAvailableLevel`。当前套餐不可用时，它不会简单推荐最高套餐，而是在个人版或企业版各自的版本序列里，找到第一个满足指定权益和 required total 的更高套餐。权益判断失败后，业务通过统一接入链路打开公共付费墙，完成升级或查看套餐详情，支付成功再刷新权益。

这项工作的个人核心产出是权益判断层、场景模型和接入规范；公共付费墙 UI 是团队协作产出，我负责把判断结果与弹窗链路打通，并推动业务接入。这样表达既能体现作用，也不会把协作成果全部说成个人完成。

### 最值得展开的技术点

- Hook 与纯函数分层：Hook 负责状态订阅，evaluator 负责可测试的领域规则。
- 类型化 context：不同场景只允许传自己需要的参数，减少业务误用。
- 额度判断统一成禁止、无限、限额三类策略，避免各业务自行猜默认值。
- “下一个可用套餐”同时考虑个人/企业版本线和具体 required total，不做硬编码跳转。

### 常见追问

**为什么不只提供一个 `isAvailable` 字段？**

业务动作常常需要上下文。例如套餐允许协作，不代表新增两个人后仍未超额；云设备支持扩容，也不代表目标规格不超过上限。因此平台提供原始权益和统一 evaluator，业务只补充动作上下文。

**14 个场景怎么说更准确？**

这是首期技术方案中的场景模型口径，覆盖协作、自定义模型/Agent、本地与云端 Agent、云设备增购/扩容、Sandbox 和 SandboxHub 等类别。后续业务仍在演进，所以不要说当前代码里永远只有 14 个枚举。

**如何推动全部业务方接入？**

先提供稳定 Hook、纯函数、场景 context 和付费墙入口，再用接入示例明确业务只需要提供哪些参数；对于判断边界不清的场景，与后端和业务 owner 确认“原始权益归平台、当前用量和动作参数归业务”的责任划分。

## 6. SIM 编辑态大表格性能优化

### 一句话定位

通过重新设计表单状态与更新粒度，把约 1400 个编辑单元格的查看态到编辑态耗时从 10 秒降到 1.8 秒。

### 30 秒版

我在 StreamHub 商业化 CRM 团队优化过一个销售业绩核算表格。查看态约 1000 个单元格，编辑态约 1400 个，切换编辑时耗时超过 10 秒。我先通过性能分析和移除实验定位到每个单元格的 `Form.Item` 注册与全量渲染是主要瓶颈；去掉 Form 后虽然降到约 5 秒，但 Context 更新仍会让所有单元格刷新并造成输入延迟。最后我用 ref 保存草稿值、发布订阅只通知受影响单元格，再结合每页 25 行、懒加载和选项按需加载，把线上交互到下一帧可见的耗时降到 1.8 秒，提速约 82%。

### 90 秒展开版

这个表格服务于季度销售业绩核算。查看态是 79 行乘 12 列的树形表格，约 1000 个单元格；编辑态展开到 79 行乘 18 列，约 1400 个单元格，并且存在校验和字段联动。原方案为了开发效率，在每个编辑单元格里使用类似 Ant Design 的 `Form.Item`。点击编辑后，表单注册、组件渲染和自定义 column render 同时发生，线上从点击到下一帧可见超过 10 秒。

我先用 Performance、React DevTools 和对照实验定位问题：删除业务 column render 或 `Form.Item` 后耗时显著下降，证明瓶颈不是接口，而是同步渲染。第一步去掉 Form，耗时降到约 5 秒，但我最初用 Context 管理数据和更新函数，一个字段变化仍会让全部消费者重新渲染，`memo` 也绕不过 Context value 变化，还出现接近 1 秒的输入延迟。

最终我把数据和视图更新拆开：ref 保存整张表的草稿值，更新函数保持稳定；每个单元格按字段订阅事件，输入时只写 ref 并通知自己或确实被联动影响的单元格。提交时再一次性读取草稿并校验。之后又增加每页 25 行、懒加载占位输入框、options 按需加载和 loading 状态，最终把同一线上埋点口径从 10 秒降到 1.8 秒。

### 最值得展开的技术点

- 用删除/替换实验定位 `Form.Item` 和自定义 render，而不是只凭感觉判断“大量 DOM”。
- ref 存数据不触发 React 更新，发布订阅把更新粒度从整表收敛到单元格。
- 联动不是取消，而是由依赖关系精确通知受影响字段。
- 分页和懒加载减少首批挂载量，状态模型优化减少后续交互重渲染，两者解决不同阶段。

### 常见追问

**为什么 `React.memo` 没解决？**

单元格直接消费了会变化的 Context，只要 Provider value 改变，消费者就会重新渲染，`memo` 不能拦住 Context 更新。发布订阅让组件只订阅自己的字段事件，才真正缩小更新范围。

**为什么不用虚拟列表？**

表格有树形层级、动态高度、复杂编辑组件和字段联动，直接上虚拟化的改造与回归成本较高。当前通过状态粒度、分页和懒加载已经达到 1.8 秒；如果数据规模继续增长，我会在行高和焦点行为可控后再评估行虚拟化。

**为什么不做单元格即时保存？**

业务要连续修改多项后统一保存，单格保存会增加接口开销、多人修改冲突和重复触发复算确认弹窗，反而打断操作流程。

**10 秒到 1.8 秒如何测量？**

简历里简称 INP，实际业务埋点是在点击编辑时记录 `performance.now()`，编辑态提交后通过 `requestAnimationFrame` 记录下一帧可见时间，并在线上保持同一口径对比。它是这次交互的自定义 interaction-to-next-paint 耗时，不应冒充 Web Vitals 对整页多次交互聚合后的标准 INP。

## 7. Account List 跨团队复用能力

### 一句话定位

把接近 2000 行的 Account 列表页面收敛成可配置 Widget，通过 Module Federation 提供给 触达团队 团队，支撑潜客批量选择和邮件触达。

### 30 秒版

StreamHub 商业化 CRM 的 触达团队 团队需要复用 Account 列表，批量选择潜客后发送邮件等操作。直接复制原页面会导致两套数据和交互逻辑长期分叉，所以我把核心 List 封装成稳定 Widget，通过 Module Federation 暴露 `AccountMyBoBList`；同时提供列与筛选项显隐、行操作开关、批量操作插槽和选中行回调。这样二方可以按场景裁剪 UI，但仍复用同一份列表逻辑和数据口径。

### 90 秒展开版

这个需求的业务背景是，销售会把潜在客户加入 触达团队，再按既定步骤发送邮件或跟进。原流程缺少批量能力，需要逐个处理；触达团队 团队因此希望直接复用 Account 列表，完成筛选、勾选和批量触达。

难点在于原页面接近 2000 行，还依赖大量样式、配置和业务逻辑。如果二方复制代码，短期看交付快，长期却会形成两套筛选、列配置和交互实现，数据口径也容易漂移。我没有直接搬页面，而是在 Widget 层增加稳定包装，将原列表作为核心实现复用，再通过 Module Federation 暴露远程模块。

为了让同一组件适配不同场景，我把差异收敛成明确接口：列和筛选项使用白名单控制，摘要、创建按钮、行操作等区域可以独立显隐；批量操作区提供 React 插槽，二方可以注入自己的按钮；列表选中数据通过回调传出，用于发送邮件等后续动作。最终二方无需维护列表副本，也能按自己的业务界面组合能力。

### 最值得展开的技术点

- Module Federation 解决运行时模块复用，Widget 接口才真正定义跨团队边界。
- 配置项控制稳定差异，插槽承载开放扩展，避免给每个业务动作增加专用布尔参数。
- 选中行通过明确回调输出，列表只负责选择，不反向依赖 触达团队 的邮件业务。
- 复用同一核心列表，避免筛选、列配置与数据逻辑形成两套实现。

### 常见追问

**为什么不直接抽成 npm 组件包？**

原页面体量大，并依赖同一应用内的样式、配置和业务模块；立即下沉为通用包会扩大改造范围。Module Federation 允许先在原应用边界内复用成熟实现，再通过稳定 Widget API 隔离二方，是交付速度和长期边界之间更合适的取舍。

**怎么避免配置项越来越多？**

把差异分三类：稳定的显隐和白名单用配置；开放的业务操作用插槽；跨边界的数据用回调。新增需求先判断属于哪一类，不为每个具体按钮追加定制接口。

**这个项目的重点是 Module Federation 吗？**

不是。MF 只是传递模块的手段，真正的难点是识别哪些逻辑必须保持单一来源、哪些 UI 可以由二方配置，以及如何让列表与批量触达业务解耦。

### 补充案例：Starling 常量文案初始化时序

一个国际化问题表现为 Starling 已经加载了正确翻译，但页面仍展示代码中的兜底文案。根因是文件顶部常量在模块 import 时立即求值，当时 Starling 尚未初始化，之后即使翻译资源就绪，常量也不会重新计算。我给出两层修复：把依赖国际化的常量改成调用时求值的方法；应用入口先等待 `initStarling`，再动态 import 主业务模块，从模块执行顺序上消除竞态。这个案例适合用来说明 ESM 模块求值时机和异步初始化边界。

## 四、远帆软件实习

## 8. qiankun 微前端基础设施与 Vite 子应用兼容

### 一句话定位

解决 qiankun 基于传统脚本执行模型与 Vite ESM 开发模式之间的冲突，并统一主子应用路由和静态资源基址。

### 30 秒版

我在远帆软件推动前端工程接入 qiankun，其中最大的难点是 Vite 子应用兼容。qiankun 的 `import-html-entry` 会把脚本放进沙箱用普通 script/eval 执行，而 Vite dev 保留 ESM 的 import/export，二者会直接冲突。单纯把生产包改成 UMD 只能解决生产集成，还会影响 code splitting，也解决不了运行时 public path。最后我用 `vite-plugin-qiankun` 适配生命周期与加载方式，并分别用 `server.origin` 和 `base` 处理开发、生产资源路径，配合主子路由同步和图片资源处理，实现多技术栈应用统一接入。

### 90 秒展开版

项目要把不同技术栈的前端应用统一挂到一个基座里。Webpack 子应用相对成熟，但 Vite 在开发环境是原生 ESM：源文件里的 import/export 不会被转成普通脚本。qiankun 的 `import-html-entry` 会抓取子应用资源，再在代理 window 的 eval 环境中执行；这个环境不是 `type=module`，所以会出现语法错误。

我先评估过 UMD 方案。它能让 qiankun 拿到 bootstrap、mount、unmount 生命周期，但只覆盖生产构建；Vite 的 UMD/IIFE 又不支持 code splitting，路由懒加载会受影响，而且 Vite 没有 Webpack 那种运行时 `publicPath`，多环境静态资源路径仍然不稳定。因此最终采用 `vite-plugin-qiankun` 把 Vite 子应用接入 qiankun 生命周期，并保持开发模式可用。

第二个问题是静态资源寻址。子应用里的图片如果按主应用 Origin 解析，就会请求到错误端口。我用 `server.origin` 解决开发环境资源来源，用 `base` 解决生产部署前缀；对于开发阶段仍难以稳定寻址的图片，我还写过 Vite 插件转成 base64 作为针对性处理。同时补齐主子应用路由同步和卸载清理，最终让不同框架的应用能够按同一规范接入。

### 常见追问

**为什么不用 UMD 作为最终方案？**

它只能覆盖生产构建，开发态仍不兼容；同时会牺牲 code splitting，且没有解决 Vite 运行时 public path。它是验证方向的过渡方案，不是完整基础设施。

**`server.origin` 和 `base` 分别解决什么？**

`server.origin` 告诉开发服务器生成的资源 URL 应使用哪个 Origin；`base` 决定生产构建产物的基础路径。两者对应不同阶段，不能互相替代。

**这段经历还缺什么量化证据？**

目前可确认的是完成多技术栈统一接入，但没有找到可靠的“接入多少个应用、节省多少时间”数据。面试前如果能补出真实应用数或迁移周期，会明显增强结果部分；没有证据时不要临时编数字。

把散落在本机 JSONL 日志里的 Agent 会话变成可浏览、可检索、可脱敏分享、并能回到原 Session 继续工作的个人知识库。

Agent Snapshots 是我做的 Codex 和 Claude Code 本地会话知识库。它通过 `agent-session-core` 把两类日志解析成统一时间线，再提供全文和本地语义检索、风险检测与自动脱敏、HTML/Markdown 导出，以及一键回到对应 Session 继续工作。语义检索使用本地 Ollama embedding 和余弦相似度，不需要把会话上传云端；续接时根据会话 ID 和工作目录调用 `codex resume` 或 `claude --resume`。我把解析能力抽成零运行时依赖的独立库，并让 Open Token Board 复用，避免展示和用量统计各写一套解析器后口径漂移。

### 90 秒展开版

我长期使用 Codex 和 Claude Code 后发现，本地积累了很多有价值的调试和实现过程，但原始会话是分散的 JSONL：很难按项目浏览，也很难搜索一句只记得大意的内容；直接分享原始日志又会泄露 token、Cookie、内网域名和本机路径。

我先把最底层的解析抽成 `agent-session-core`。它发现 Codex 与 Claude Code 的会话目录，把 message、tool call、tool result、token usage、compaction 等事件归一成统一时间线，并把 Codex 累计 token 快照转换为可处理 reset 的增量。核心库没有运行时依赖，查看器和 Open Token Board 都消费同一份领域模型。

上层查看器支持全文和语义搜索。语义搜索把会话按 chunk 建本地索引，用 Ollama 生成 embedding，再按 cosine similarity 找最相关片段；索引按会话 fingerprint 增量更新。分享前，检测和脱敏使用同一份规则表，覆盖私钥、JWT、GitHub/OpenAI key、Bearer token、连接串、Cookie 和 home 路径，避免“风险提示发现了，但导出没有真正替换”的规则漂移。

另一个差异点是会话续接。用户点击历史会话后，系统校验 UUID 和工作目录；如果对应终端已经运行就切过去，否则在正确目录执行 `codex resume <id>` 或 `claude --resume <id>`。所以它不只是只读归档，也把历史知识重新接回工作流。

### 常见追问

**全文搜索和语义搜索有什么区别？**

全文搜索适合记得准确关键词；语义搜索适合只记得问题大意。后者使用本地 embedding，把 query 和会话 chunk 映射到向量后计算余弦相似度，代价是需要本地 Ollama 和索引更新。

**自动脱敏是否绝对安全？**

不是。规则会偏向过度脱敏，并且检测与替换共用一个规则源；但任何规则都可能漏掉新格式，因此产品默认本地、只读，只有用户主动导出或分享才上传，并提醒发布前人工复核。

**“一键回到 Session”怎么实现？**

保存归一后的 engine、session ID 和 cwd。Codex 用 `codex resume`，Claude Code 用 `claude --resume`；先校验 UUID 和目录，优先切换已存在的对应终端，否则创建新终端。面试口述不需要提具体终端产品名。

**Gist 导出是什么意思？**

它是把脱敏后的静态 HTML 发布到 GitHub secret Gist，再生成可访问链接。secret Gist 不出现在公开搜索里，但拿到链接的人仍能访问，所以它不是权限系统，仍要先脱敏和人工复核。当前简历没有写这一点，只有面试官追问分享方式时再补充。

## 10. Open Token Board：AI 编码用量与额度平台

### 一句话定位

从 Codex 和 Claude Code 的本地日志采集可信用量与订阅额度，并把它们变成可对账的排行榜、趋势、额度预测和团队协作平台战报。

### 30 秒版

Open Token Board 是我做的自托管 AI 编码用量与额度平台。`token-board-agent` 在本机只读采集 Codex 和 Claude Code 日志，通过 `agent-session-core` 归一 token 事件，再上传到 Node API 和 PostgreSQL。普通同步靠稳定事件 ID 与数据库主键幂等；全量替换采用 `start / append / commit` 分阶段暂存，只有事件数和 digest 都一致时才在数据库事务中替换旧历史。上层提供排行榜、代码产出、Codex/Claude Code 额度 burn rate 和预计耗尽时间，并在额度过低时通过团队协作平台日报或周报预警。

### 90 秒展开版

这个项目最初是想做一个朋友间的 AI 编码排行榜，但很快发现真正困难的不是页面，而是数字可信。Codex 和 Claude Code 的日志目录、字段和累计/增量语义不同；同一文件可能出现在多个 home 或归档目录；Agent 每隔几分钟同步一次，网络重试也不能重复计数。

我的架构是本机 agent、API、PostgreSQL 和 Web 四层。agent 只读本地日志，按 inode 去重物理文件，通过 `agent-session-core` 把累计 token 快照转成增量事件，再做项目 basename、会话标题和 session ID 清洗。默认不上报 prompt、回复、文件内容、完整路径和密钥。服务端不信任客户端自报身份，并再次做字段和隐私校验。

普通同步用本地 checkpoint 减少上传量，但真正的一致性底座是稳定事件 ID 和 PostgreSQL 主键，网络超时可以安全重试。全量替换更危险，所以我设计成两层原子性：网络层先 `start` 声明 expected count 和 manifest digest，`append` 分批暂存，`commit` 校验完整性；数据库层再在一个事务里删除该用户旧数据并插入新数据。任何阶段失败都不动旧历史。

额度和用量也分开建模。用量回答“消耗了多少”；额度快照回答“5 小时或周窗口还剩多少”。Codex 从本地日志读取，Claude Code 通过 statusline capture 保存快照。系统根据剩余比例、重置时间和 burn rate 预测是否会提前耗尽，并把排行榜变化、PB、徽章和低额度预警发送到团队协作平台。

### 最值得展开的技术点

- 统一事件模型：同一份事实同时支持 token 排名、费用估算、趋势和个人画像。
- 两层幂等：checkpoint 只优化性能，稳定事件 ID 和数据库主键保证正确性。
- 两层原子性：上传 staging 保证数据到齐，数据库 transaction 保证正式切换完整。
- 用量和额度分离：token 总量不能直接推出订阅窗口剩余。

### 常见追问

**为什么 `start / append / commit` 还不够，还要数据库事务？**

staging 解决网络上传期间的数据完整性；事务解决正式数据从旧版本切到新版本时的原子性。只有前者，提交时数据库仍可能写一半；只有后者，数据没传完整前无法安全开始替换。

**怎么避免同一会话重复统计？**

发现阶段按设备号和 inode 去重同一物理文件；解析后生成稳定事件键；服务端以事件 ID 为主键并 `ON CONFLICT`。三层分别解决文件镜像、重复扫描和网络重试。

**token 口径怎么解释？**

排行榜的消费量使用输入加输出，不把缓存字段再重复相加；费用估算则把普通输入、缓存写、缓存读和输出按不同价格投影。Codex 的累计快照先转成相邻增量，遇到 compaction/reset 时按 reset-aware 规则处理。

**为什么正式部署用 PostgreSQL？**

早期 JSON 存储适合验证语义，但数据增长后 Node 全量读取和聚合会拖慢榜单。PostgreSQL 可以按时间范围过滤、分组和聚合，并通过事务与索引提供更稳定的一致性和查询性能；JSON 只保留为轻量兜底。

## 七、可作为备选的个人项目

## Chrome 接口 Mock 插件

### 30 秒版

我做过一个供实验室前端使用的 Chrome MV3 接口 Mock 插件。它把规则和响应数据存进 IndexedDB，在页面上下文中代理 `window.fetch` 和 `XMLHttpRequest`，匹配规则时直接返回 Mock Response，不匹配则透传真实请求。早期尝试过 `webRequest.onBeforeRequest` 重定向，但它无法直接修改响应体，Data URL 和动态 JSON 也有能力边界；后来改为页面脚本代理，同时通过外部 `injected.js` 和 `web_accessible_resources` 避免 CSP 阻止内联脚本。项目让前端可以不改业务代码、也不等待后端接口就开始联调。

### 可追问点

- content script 与页面 JavaScript 是不同执行世界，重写页面的 `window.fetch` 需要注入页面上下文。
- MV3 CSP 会阻止动态内联脚本，改成独立资源并在 manifest 中声明。
- IndexedDB 适合异步保存较大的结构化 Mock 配置，优于同步、容量更小的 localStorage。
