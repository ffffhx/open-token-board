## 2. 重点业务需求

### 2.1 商业化权益能力建设

流舟进入商业化阶段后，需要在用户使用受限功能时进行权益拦截与付费引导。整个权益体系经历了从 2.0 到 3.0 的演进。

#### 2.1.1 商业化权益 2.0 阶段

在 2.0 阶段，需求的核心目标是让未开通或用量超限的用户及时感知权益边界，并在操作入口弹出升级提示。

资料图：流舟编程部署页：构建次数达上限时，在「开始部署」入口弹出升级提示（附件未随本题提供：figure-01-deploy.png）

资料图：项目管理里不同套餐的权益项展示，额度来源和拦截表现并不统一（附件未随本题提供：figure-02-benefits.png）

在最初的实现中，面临的主要问题是**权益表现不统一**与**数据来源分散**：
- 部分权益（如 QPM）仅展示上限而不做前端拦截，而日志类权益则根据实时使用率触发不同的交互分支；
- 套餐额度来自商业化后端，但实时用量却分散在各个业务方的后端接口中，需要分别对接与校验。

针对这些问题，我们通过场景 Hook 将商业化套餐权益与业务后端使用量进行了聚合封装，为每个权益提供独立的判断 Hook。

资料图：权益 2.0：套餐接口进入 Benefits Store，再和业务用量一起交给各权益 hook 判断（附件未随本题提供：figure-wb-04-benefits-2-flow.jpg）

2.0 阶段最终完成了 6 类编程权益的拦截接入，为后续大规模商业化奠定了基础。

---

#### 2.1.2 商业化权益 3.0：跨端可复用架构

进入 3.0 后，流舟的权益项大幅增加，交互链路也全面升级：用户触发未授权功能时，先弹出权益拦截弹窗提示升级原因，确认升级后再进入专属支付弹窗完成购买。

资料图：权益 3.0 拦截弹窗：权限不足时先提醒升级，再进入支付流程（附件未随本题提供：figure-03-paywall.png）

在这一阶段，技术上面临着更高的复杂度和挑战：

1. **三端复用与扩展性**：Space、Coding 以及移动端存在相同的权益功能，如果继续在业务侧各自实现，会导致严重的逻辑冗余与维护成本；
2. **多维度的套餐推导逻辑**：单纯向上一档推荐往往无法满足用户新增的用量需求；个人版、团队版与企业版的权益形态各异，且必须向前兼容历史老套餐、向后兼容未来新增套餐；
3. **需求分散与链路协同**：商业化逻辑分散在 8 个具体的业务需求之中，且部分扩容信息无法由商业化后端统一提供，需要各业务方后端提供独立接口并在前端收口。

为了彻底解决跨端与复用问题，我们设计了**业务逻辑与 UI 视图彻底解耦**的架构方案：

- 抽象出独立的无头能力：统一的「权益拦截判断」与「套餐推导规则」，不依赖任何特定页面 UI，可直接供 PC 端、移动端多场景复用；
- 统一步骤调用契约：调用方只需传入权益类型与本次操作的新增用量，后续的拦截判定、推荐套餐推导、付费墙文案组装及支付跳转全流程均由商业化统一处理。

资料图：左侧是统一权益判断，右侧是历史套餐映射与额度匹配的套餐推导（附件未随本题提供：figure-wb-01-benefits-capability.jpg）

资料图：调用方只传权益类型和新增量，商业化侧完成判断、套餐推导、拦截弹窗和支付（附件未随本题提供：figure-wb-05-benefits-3-seq.svg）

### 2.2 流舟编程：部署 Trace 与分析

这是我入职第一周独立接手的第一个业务需求。

资料图：部署 Trace：对话侧的一次生成，对应到 Trace ID、Token 和输入输出（附件未随本题提供：figure-04-trace.png）

资料图：部署后的分析页：用户活跃、留存和代码侧的 Agent 运行结果（附件未随本题提供：figure-05-analytics.png）

刚入职时，面对完全陌生的业务背景与代码库，我经历了人机协同方式的探索与转变：

起初我尝试过规范化的 Spec-Driven 开发模式，但在实际高频迭代中很快发现了其局限性：
- **Spec 文档极易过时**：业务需求在变、同事在合入代码，文档写完即脱离真实上下文，而过期的文档对 Agent 是严重干扰；
- **文档冗余且信息密度偏低**：生成的 Proposal、Design 和 Tasks 动辄上千行，人工逐行 Review 容易成为效率瓶颈；
- **产生「文档即交付」的错觉**：真正的集成问题（接口参数变动、存储时机差异）往往只有在真实运行时才能暴露。

在此之后，我调整了人机协同的工作流，形成了更加实用的协作闭环：

1. **方案与范围对齐（~80%）**：先与 Agent 对齐需求背景、职责边界和架构设计（哪些复用、哪些新建、归属哪个 Package）；
2. **定义验收标准并提供工具**：聊清核心交互流程，配备切换账号、数据 Mock 等工具让 Agent 自主执行验证；
3. **大任务拆分子会话**：复杂需求按模块拆分为多个独立 Session，主 Session 负责推进进度与统筹；
4. **自主编码与小步验证**：Agent 结合现有代码库与相关文档自主完成编码与自测，最后由人工进行兜底验证与微调。

### 2.3 流舟商业化：套餐升降配与订阅管理优化

用户在日常使用中会产生升配、降配或平级切换套餐的需求，旧版本由于缺乏统一收口，用户体验不够连贯。

资料图：套餐页：个人免费 / 进阶 / 高阶 / 旗舰，订阅周期和附加权益都不一样（附件未随本题提供：figure-06-plans.png）

资料图：订阅管理：当前套餐、可切换选项和购买记录（附件未随本题提供：figure-07-subscription.png）

这块业务的复杂性集中在两点：
- **规则维度交织庞杂**：原订阅渠道、目标订阅渠道、付费周期、原套餐版本及目标版本等多维因素交织，共衍生出 47 条分支规则；
- **账号构造困难且测试成本高**：特定渠道（如苹果内购、CRM 订阅）的测试账号构造繁琐，且很多测试账号一经使用订阅状态即改变，无法重复测试，再加上 A/B 实验分流，测试难度倍增。

资料图：个人版和团队版的套餐变更规则树：升 / 平 / 降 × 订阅渠道 × 周期（附件未随本题提供：figure-wb-02-subscription-rules.jpg）

**应对方案**：
通过 AI 辅助系统化梳理 47 条规则树，将前端用户表现收敛为「生效中」与「待生效」三大类统一弹窗交互；同时让 AI 针对指定接口字段生成并沉淀了标准 Mock 规则集，极大降低了后续开发与联调的验证成本。

## 3. 重点技术建设

### 3.1 商业化域代码组织结构重构

商业化能力最初分散在历史遗留包 `packages/studio` 中，与大量非商业化代码混杂在一起，逐渐积累了严重的架构坏味道：
- **依赖方向倒置**：本应作为底层基础的 `subscription-common` 反向依赖了上层 UI 包 `subscription-paywall`；
- **缺乏统一对外出口**：外部业务方为了复用部分能力，不得不深路径引用内部实现文件，导致内部稍作重构外部调用方就会大面积报错；
- **公共能力缺乏收口**：付费墙导航等基础能力在各处被随意拼装，UI、领域逻辑和页面编排深度耦合。

资料图：外部包只走 commercial entry；向下是 feature / shared / core 的单向依赖（附件未随本题提供：figure-wb-03-commercial-arch.jpg）

我们确立了 **Feature-first + 分层依赖约束** 的架构方案：

1. **清晰的 4 层单向依赖结构**：自底向上划分为 `core`、`shared`、`feature`、`entry`，严格禁止跨层反向依赖，并配置 ESLint 规则进行自动化卡口；
2. **受控的对外出口（Entry）**：仅对外暴露经过抽象的 88 个 API，刻意杜绝 `export *` 通配导出，确保内部实现能够持续演进而不影响外部依赖；
3. **分批次平稳迁移**：先搭建新目录结构与依赖边界，再迁移共享基座，随后迁移核心业务流程，最后分批替换业务方引用并清理旧包。

本次重构共覆盖 **518 个逻辑变更文件**，收拢落地为 6 个子包，在业务高速迭代的同时实现了零故障平滑过渡。

### 3.2 FlowDesk 测试账号切换工具链

在商业化开发与验证过程中，经常需要在不同权限与套餐的测试账号之间切换。过去依赖查表找账号、退出并重新登录，单次操作耗时通常在 2 分钟以上。

资料图：账号切换插件：在已登录页面上选择目标账号并一键切换（附件未随本题提供：figure-08-account-switch.gif）

为了兼顾开发效率与安全性，工具链经历了三代方案演进：

- **第一代（Playwright 模拟点击）**：自动填写账号密码并点击界面，但遇到 UI 结构调整时极易失效，耗时且不稳定；
- **第二代（直接调用登录/退出接口）**：绕过了大部分 UI 交互，但需额外处理反爬动态签名，且遇到需要短信验证的企业主账号时无法直接完成；
- **第三代（UID 换取 Session Cookie 替换）**：通过后端服务直接使用目标 UID 换取合法 Session 并注入当前环境，大幅简化了操作链路；切回本人账号时，通过带有 `prompt=none` 参数的 Tab 跳转静默复用团队协作平台登录态。

同时，工具链通过企业云与 AccessGate 实现了双重身份校验，确保测试账号与敏感 Session 的访问安全，并提供了 Chrome 插件与 CLI 双入口，完美支持人和 Agent 共同调用。

资料图：先换业务 Token，再按「切回本人 / 切换测试账号」两条路径完成校验（附件未随本题提供：figure-wb-06-account-seq.svg）

**产出成果**：账号切换耗时从 2 分钟以上缩短至 **10 秒以内**，目前已在组内 10+ 同学中日常使用。

### 3.3 通用 AI 工程化：ProfilePilot

在商业化拦截与支付流程中，大量场景必须由 Agent 在真实登录态下操作页面完成验证，而支付环节又需要人工介入。

我们对市面上 6 款主流浏览器自动化工具进行了多维度评测（详见内部 Wiki：[Agent浏览器控制工具测评](https://reference.invalid/source/014)），发现现有工具普遍无法解决「开发者与 Agent 抢占同一个 Chrome 窗口与焦点」的问题。

资料图：ProfilePilot：给多个隔离 Profile 分配端口、同步登录态，并查看 Agent 占用（附件未随本题提供：figure-09-profilepilot.png）

资料图：真实页面上的 Agent 控制条：任务进行中可暂停、继续，人和 Agent 不抢同一个窗口（附件未随本题提供：figure-10-agent-overlay.png）

针对这一痛点，我设计并落地了 **ProfilePilot** 控制台：

- **Gateway 统一管理**：集中管理多个已登录的 Chrome Profile 资源与租约，动态分配空闲 Profile 给 Agent Session；
- **受控 CDP 通信**：Wrapper 解析命令并向 Gateway 申领一次性 Ticket，Daemon 通过 WebSocket 建立长连接，CDP 指令经 Gateway 安全校验后通过专用管道转发；
- **可见可接管**：在页面注入悬浮控制条，开发者可随时暂停、接管或恢复 Agent 任务，两者互不干扰。

资料图：ProfilePilot 双核架构：左翼可编程 Agent 协同控制面与右翼本机优先 Profile 数据管理面（附件未随本题提供：figure-wb-08-profilepilot-arch.svg）

资料图：Agent 不带 --session 发命令，由 Gateway 原子绑定 Profile 并签发一次性 Ticket（附件未随本题提供：figure-wb-07-profilepilot-seq.svg）

**产出成果**：支持日常并行运行 3 个独立的 Agent 浏览器 Session，实现多需求并行开发与自动化验证。

## 5. 反思与成长

- **理解业务与对齐上下文比单纯写代码更关键**：很多复杂需求的瓶颈不在编码，而在跨角色沟通、评审物料获取以及清晰界定能力边界；
- **保持敏锐，主动拥抱前沿模型**：AI 工具与开发范式迭代极快，不应固守静态规范，积极使用最新 SOTA 模型探索最契合当下的人机协作流；
- **工程师核心价值的转变**：死记语法和基础 API 已不再是壁垒，真正稀缺的是对复杂业务的穿透理解力、清晰的专注力以及架构与技术方案的工程判断力。
