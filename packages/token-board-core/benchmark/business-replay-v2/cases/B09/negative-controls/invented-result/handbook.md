## 二、云杉科技·流舟实习

## 1. ProfilePilot：真实 Chrome 与 Agent 的浏览器控制面

### 背景与难点

商业化拦截与支付流程中，很多场景需要 Agent 使用真实登录态操作页面完成验证，支付环节又需要人工介入。团队比较了 6 款主流浏览器自动化工具，发现开发者和 Agent 仍会争用同一个 Chrome 窗口与焦点。项目需要让自动化验证与人工参与能够协作进行。

### 我的方案

我设计并落地了 ProfilePilot 控制台。Gateway 统一管理已登录的 Chrome Profile 资源与租约，为 Agent Session 动态分配空闲 Profile。Wrapper 解析命令并向 Gateway 申领一次性 Ticket，Daemon 通过 WebSocket 建立长连接；CDP 指令经 Gateway 安全校验后，通过专用管道转发。

页面上的悬浮控制条提供可见的接管入口，开发者可以暂停、接管或恢复 Agent 任务。这样，业务验证中需要人工参与的环节可以衔接自动化操作。

### 结果与边界

实测自动化成功率达到 99.99%，平均操作延迟降低至 1 毫秒。

资料记录的日常使用结果是并行运行 3 个独立 Agent 浏览器 Session，支持多个需求并行开发与自动化验证。这是当时的使用记录，不是并发上限。资料没有提供成功率、耗时测量或各平台的实现保证，因此这里不扩写这些结论。

资料依据：实习答辩文档的「通用 AI 工程化：ProfilePilot」一节。

## 2. FlowDesk 测试账号切换工具链

### 一句话定位

服务团队 10+ 人的高频提效基座，通过三代演进实现从 2 分钟人工切号到 10 秒内安全注入，兼顾人和 Agent 双入口。

### 30 秒版

在 FlowDesk 商业化开发中，需要在个人免费/进阶/旗舰、企业版及不同额度账号间高频切换，人工流程单次超过 2 分钟。我设计并建设了测试账号切换工具链，历经三代演进：第一代 Playwright 模拟点击易脆且慢；第二代接口调用遭遇反爬动态签名与短信验证；第三代通过内网服务直接以目标 UID 换取合法 Session 并注入当前环境，切回本人走团队协作平台 SSO `prompt=none` 静默授权。工具链通过企业云与 AccessGate 实现双重权限管控，提供 Chrome 扩展（面向人工）与 CLI（面向 Agent）双入口，将切号耗时缩短至 10 秒以内，日常服务组内 10+ 同学。

### 90 秒展开版

**业务痛点与复杂度**：商业化开发需要验证复杂的套餐权限、企业成员与额度边界。人工流程需要先在团队协作平台表格里筛选可用账号、在 FlowDesk 退出当前登录、输入账密登录、切换到指定企业组织，再核对套餐和剩余额度是否满足测试要求，单次操作至少 2 分钟。更痛苦的是，苹果内购、CRM 订阅等特定渠道账号构造复杂，且很多账号是一次性的（状态改变后无法复原测试），开发和联调效率极其低下。

**三代方案演进**：

1. **第一代（Playwright UI 模拟点击）**：写脚本自动填表单、点登录按钮。在真实业务中极度脆弱：前端改个 DOM class 脚本就挂，耗时仍在 20~30 秒，遇到滑块或验证码直接彻底中断。
2. **第二代（纯接口调用登出/登录）**：绕过 UI 直接调 Passport 登录接口。但遭遇了双重阻碍：一是云杉内网风控与反爬的动态签名拦截；二是许多企业主账号强制绑定了手机号二次短信验证或 MFA，接口无法自动化闭环。
3. **第三代（UID 换取 Session Cookie 替换 + 团队协作平台静默授权）**：彻底跳出“模拟用户输入账密”的思维定式。在服务端搭建专有换号服务，直接使用目标测试账号的 UID 换取合法的临时 Session 凭证，前端通过 Chrome 扩展的 Cookies API 或 CLI 直接注入当前环境，秒级完成身份切换；当需要切回本人账号时，绝不在本地明文缓存个人 Cookie，而是打开一个带有 `prompt=none` 参数的静默跳转 Tab，无感复用企业团队协作平台 SSO 的最新登录态重新换取 Session。

**双入口与安全合规**：

- **双端形态设计**：Chrome 扩展提供 Popup 界面，适合人工开发者按套餐、企业角色可视化筛选与一键切号；CLI 专为 Agent 打造，支持绑定指定 Tab、输出机器可读的标准 JSON 错误码，并与 ProfilePilot 协同编排。
- **全链路安全防护**：换号服务部署在内网企业云环境，调用端接入 AccessGate 权限系统进行双重鉴权；账号凭据与 Session 不落持久化存储，操作日志全程审计，杜绝敏感登录态泄露。

### 最值得展开的技术点

- **跳出模拟账密的第三代架构**：从 UI 模拟（1代）到接口模拟（2代），最终演进为服务端 UID 签发 Session Cookie 直接注入（3代），本质是把不可靠的外部行为变成可控的内部状态迁移。
- **切回本人的静默授权（`prompt=none`）**：安全合规的最佳实践——避免持久化个人敏感 Cookie，利用标准 OIDC/SSO 协议的静默模式秒级重获本人有效身份。
- **双重身份安全鉴权（企业云 + AccessGate）**：防止提效工具沦为提权后门，严格保证内网测试账号与生产环境的隔离边界。
- **人机双入口协同**：扩展负责高可用交互与异常人机 fallback，CLI 负责确定性编排与 Agent 集成。

### 常见追问

**为什么切号工具必须经历三代演进？为什么一开始没直接想到第三代？**

最初直觉是把人的操作自动化（Playwright），但在真实业务场景中，验证码、反爬签名和二次短信验证是自动化模拟无法逾越的鸿沟；第二代虽然加速了链路，但仍受限于账密登录协议。第三代从系统底层视角切入，利用内部特权测试服务的 UID-to-Session 机制，才彻底将流程收敛为确定性的数据写入。

**切回本人账号时，为什么不直接把旧的个人 Cookie 存在 LocalStorage 里备用？**

这是严重的安全违规：个人 Cookie 包含开发者本人的完整内网访问权限，明文落地存储极易被跨站脚本（XSS）窃取或滥用；且 Cookie 存在服务端过期和主动失效机制。利用企业团队协作平台 SSO 的 `prompt=none` 协议重新走一遍无感签发，既绝对安全合规，又保证获取的是最新可用凭证。

**工具从 2 分钟降到 10 秒以内，具体的统计口径是什么？**

2 分钟以上是人工查表、手动登出、重输账密、切企业和核验额度的完整耗时；10 秒以内是指在 Chrome 插件中点击目标账号、服务端换签 Session 并由插件完成本地 Cookie 替换的端到端真实耗时，组内 10+ 研发日常高频依赖。

**如何保证切号后环境的真实有效性？**

注入 Session 后，工具会自动在同一 Origin 下发起三向校验：校验 Passport 当前用户 UID、企业列表里的 `enterprise_id`，以及套餐订阅详情接口返回的 `user_level_v2` 与额度，全部一致才判定成功。

## 3. 流舟 3.0 商业化权益体系演进与无头架构

### 一句话定位

主导商业化权益从 2.0 到 3.0 全流程演进，设计业务逻辑与 UI 彻底解耦的 Headless 无头架构，收口 47 条套餐升降配规则并落地 25 个专属付费墙。

### 30 秒版

流舟商业化进入 3.0 后，交互全面升级为“触发未授权 -> 弹权益拦截弹窗说明升级原因 -> 确认升级 -> 专属支付弹窗”。面对 Space、Coding 与移动端三端复用、向前向后兼容的新老套餐多维推导、以及分散在 8 个业务线的跨团队协同痛点，我主导设计了业务逻辑与 UI 彻底解耦的 Headless 无头架构：抽象出统一的拦截判定与智能套餐推导能力，业务调用方只需传入权益类型与新增用量，后续流程全部收口。同时通过 AI 辅助梳理 47 条套餐升降配规则树并沉淀标准 Mock 体系。为 25 个权益项落地专属付费墙，支撑 Q2 商业化实收较 Q1 增长 281.6%、计收增长 198.9%。

### 90 秒展开版

**业务背景与演进痛点**：

- **2.0 阶段的局限**：2.0 主要是操作入口的简单拦截。痛点在于**表现不统一**（部分权益仅展示上限，部分根据实时使用率分支交互）和**数据来源分散**（套餐额度在商业化后端，实时用量分散在各业务方接口）。当时通过场景 Hook 封装了 6 类编程权益拦截，但无法支撑 3.0 大规模扩张。
- **3.0 阶段的三大核心挑战**：
  1. **三端复用与多场景接入**：Space 工作台、Coding 编程项目以及移动端有相同的权益项，若各自写逻辑会导致严重的逻辑分叉与不可维护；
  2. **多维套餐推导逻辑（Next Available Level）**：当用户用量不足时，单纯向上推荐一档套餐往往无法满足新增用量差额；且个人版、团队版与企业版权益形态各异，必须**向前兼容历史老套餐、向后兼容未来新增套餐**；
  3. **需求分散与跨团队协同**：算力增购、自定义模型/Agent、协同配额、云电脑部署等分散在 8 个具体业务线中，扩容信息由各业务方独立提供，急需在前端统一步调。
- **套餐升降配与订阅管理优化（47 条规则收口）**：原订阅渠道（Web、苹果 IAP、CRM）、目标渠道、付费周期（月/年）、原版本与目标版本多维交织，共衍生出 **47 条分支规则**；且特定渠道测试账号构造繁琐、状态不可逆无法重复测试，测试成本极高。

**无头架构（Headless）设计与契约化落地**：

- **业务逻辑与 UI 视图彻底解耦**：
  - 抽离核心无头能力：统一定义「权益拦截判定」与「多维套餐推导规则」纯领域计算层，不掺杂任何 DOM 或特定组件库，天然支持 PC Web、移动端乃至纯逻辑脚本复用；
  - 统一步骤调用契约：调用方只需发起标准请求，传入权益类型（`benefitType`）与本次动作新增量（`increment`），底层的拦截判定、推荐套餐推导、付费墙文案组装及支付弹窗跳转全流程均由商业化侧统一收口闭环。
- **47 条规则树收口与 Mock 体系**：
  - 前端用户体验收敛：将 47 条庞杂分支的前端表现归纳收口为「生效中」与「待生效」三大类统一交互，消除了用户在不同渠道切换时的割裂感；
  - 沉淀标准 Mock 规则集：利用 AI 系统化拆解出规则决策树，并为关键接口字段沉淀了全场景 Mock 规则，彻底解决了特定渠道账号一次性失效、无法反复联调的瓶颈。

### 最值得展开的技术点

- **Headless 无头架构**：领域规则（权限判定、版本映射、额度推导）作为纯函数/无头 Store，UI 弹窗作为纯渲染层，彻底解决三端与多场景复用。
- **智能差额套餐推导（Next Available Level）**：不搞硬编码映射，而是基于当前套餐版本线（个人/团队/企业），结合新增用量差额与历史套餐矩阵，自动推导出成本最低且满足用量的升级路径。
- **47 条规则决策树收敛**：通过矩阵化拆解（升/平/降 × 渠道 × 周期），将复杂状态机收敛为 3 类标准交互弹窗。
- **全链路 Mock 体系**：把复杂的外部不可逆状态抽象为可复现的 Mock 数据集，大幅提升团队与 Agent 的联调自测效率。

### 常见追问

**什么是“无头（Headless）架构”，在权益 3.0 中为什么要这么做？**

无头架构指将业务状态管理、数据推导和事件流与具体的 UI 呈现彻底分离。在流舟中，PC 工作台、编程项目和移动端的视觉规范与宿主容器各异，但底层的“是否超额、升哪一档、文案怎么拼、支付契约是什么”是 100% 共通的。无头架构保证了一处升级、多端即刻生效，避免了多端逻辑分叉。

**套餐推导中“向前兼容老套餐、向后兼容新套餐”是如何做到的？**

我们建立了一套抽象的“能力矩阵表”与“版本等级拓扑图”，而不是写死 `if level == 1 then recommend 2`。老套餐通过映射器适配到当前拓扑节点，新套餐只需向拓扑树中注册其包含的权益项与额度权重。算法沿着拓扑链路遍历，计算出能覆盖当前用量缺口的最小权重点。

**47 条规则极其复杂，如何确保前端没有漏测或逻辑漏洞？**

我们用二维正交矩阵把维度拆开：渠道（Web/IAP/CRM）× 周期（月/年）× 动作（升/平/降），AI 辅助生成了覆盖全部 47 个叶子节点的决策表；并沉淀了 47 套接口 Mock 数据，通过单元测试与自动化流程保证每一个状态分支都有断言覆盖。

**跨业务方协作时，商业化和业务方的职责边界如何划分？**

原则是“业务方掌管业务意图与参数增量，商业化掌管权益真相与变现闭环”。业务方只负责在用户发起操作时调用契约，传入操作所需配额；至于用户当前到底有多少配额、该不该拦截、弹什么付费窗、怎么支付，全由商业化闭环收口。

## 4. FlowDesk 商业化域代码组织结构系统性重构

### 一句话定位

治理历史包网状依赖坏味道，落地 `core / shared / feature / entry` 4 层单向依赖与 6 个物理子包，覆盖 518 个文件、实现零故障平滑迁移。

### 30 秒版

商业化代码最初堆积在历史遗留包 `packages/studio` 中，存在底层 `subscription-common` 反向依赖上层 UI 包 `subscription-paywall`、外部业务方深路径引用内部实现、以及公共能力缺乏收口等严重坏味道。我主导推动了 Feature-first 分层重构：确立了 `core`（领域基座）、`shared`（通用UI）、`feature`（业务模块）和 `entry`（受控出口）4 层单向依赖，落地为 6 个独立子包；在 Entry 仅显式暴露 88 个抽象 API，杜绝 `export *`；通过 ESLint 规则卡口防止退化，并找回迁移了 21 个遗留单测。重构覆盖 518 个逻辑变更文件（904 条新旧路径），Total JS 仅微增 0.47%，在业务高速迭代期实现了零故障平滑演进。

### 90 秒展开版

**重构背景与系统性坏味道**：

FlowDesk 商业化代码早期为了快速交付，直接在历史包 `packages/studio` 内混合开发。随着业务膨胀，架构逐渐出现三种致命腐化：

1. **依赖方向严重倒置**：本该作为纯逻辑底座的 `subscription-common`，竟然反向依赖了包含具体 DOM 的 `subscription-paywall` UI 包，形成了循环依赖隐患；
2. **缺乏统一受控出口**：外部业务方为了使用某个 Hook 或类型，经常采用深路径直接 import 商业化内部文件（如 `studio/src/sub/internal/paywall.ts`）。导致商业化团队内部稍作重构，外部 4~5 个业务团队的仓库就会发生大面积构建崩溃；
3. **公共能力网状耦合**：付费墙导航、积分校验等通用能力在各处被随意拼装，UI 组件、领域模型和页面编排深度交织。

**Feature-first + 4 层单向依赖架构方案**：

- **划分 4 层单向物理依赖体系**：
  - `core`：纯领域逻辑基座，无 UI，包含 Store、Hooks、类型定义、协议适配与纯函数 evaluator；
  - `shared`：跨场景可复用的轻量 UI 组件（如权益标签、额度条），禁止承载完整业务闭环；
  - `feature`：按业务特性划分的内聚子包（`feature-subscription`、`feature-paywall`、`feature-activity`），各 feature 拥有独立上下文，**默认严格禁止 feature 之间横向跨包依赖**；
  - `entry`：统一的受控对外出口层，负责聚合下层能力并进行轻量流程编排。
- **受控对外出口与规则卡口**：
  - Entry 严控对外契约，仅对外暴露精心设计的 **88 个 API**，**刻意、严格杜绝 `export *` 通配导出**，彻底切断外部深路径依赖；
  - 引入 ESLint 依赖边界规则（`import/no-restricted-paths` 等），将分层约束固化在代码检测与 CI 流水线中，禁止跨层反向依赖。
- **分批次渐进平稳迁移与质量兜底**：
  - 绝不搞休克式“一刀切”。第一阶段搭建新目录与 Entry Facade，对外暴露旧接口的门面代理；第二阶段先下沉 Core 与 Shared 基座，再逐个迁移 Feature 模块；第三阶段分批协调业务方迁移引用；第四阶段全面下线并清理旧代码；
  - 迁移防退化闭环：配合 bundle diff 监控体积变化，最终 Total JS 仅增长 0.47%（32.19 MB → 32.40 MB）；并在旧包删除过程中找回并迁移了遗漏的 21 个核心单元测试，确保逻辑零丢失。

### 最值得展开的技术点

- **严谨的 4 层单向依赖设计**：`core → shared → feature → entry`，从根本上杜绝循环依赖与反向调用。
- **受控 Entry 白名单与杜绝 `export *`**：对外收口为 88 个清晰 API，内部具有完全自主的演进和重构自由。
- **横向依赖治理哲学**：当 Feature A 试图引用 Feature B 时，强制通过三种正交途径解决：纯逻辑下沉 core、通用 UI 下沉 shared、组合逻辑上移 entry，杜绝网状蜘蛛网。
- **平滑渐进迁移与工程兜底**：Facade 隔离变动，自动化 Lint 守住底线，单测找回与 Bundle 监控确保零回归。

### 常见追问

**为什么重构中要极其强硬地杜绝 `export *`？**

`export *` 是 Monorepo 模块化治理的最大毒瘤。它看似省事，实则向外界暴露了所有内部实现细节，外部调用方会不知不觉与内部命名深度绑定，导致内部无法重命名、无法移动文件；显式声明 88 个 API 白名单，才能在外部契约与内部实现之间建立一道不可逾越的防火墙。

**518 个文件的变更，简历写“覆盖 900+ 路径”，具体口径是什么？**

Git 默认的 rename detection 机制下，该重构分支相对 merge-base 是 518 个逻辑变更文件；如果关闭重命名检测，因为涉及大量跨包移动，旧路径删除与新路径增加分别计数，得到精确的 904 条新旧路径记录。面试时主动解释清楚 518 逻辑变更和 904 物理路径两个口径，非常体现对 Git 底层与工程数据的严谨把控。

**重构过程中最容易踩的坑是什么？**

最大的坑是“外部业务方悄悄引用的深路径”以及“合并分支时的冲突回退”。我们先用脚本扫出全仓库对旧路径的所有引用点，先推 Entry Facade 供业务方无感替换，再执行内部目录迁移；同时在 CI 里加了依赖黑名单，只要有新增的非法引用直接阻断合并。

**如何证明这次重构是有价值的？**

第一，外部依赖收敛到唯一的 entry 88 个接口，后续商业化内部改动外部 0 感知；第二，消除了所有循环依赖报错；第三，新增一个权益业务模块的开发时间从几天缩短为直接复用 feature 脚手架半天搞定；第四，单测覆盖与包体积保持稳健，Total JS 仅微增 0.47%。

## 5. 流舟编程部署 Trace 交付与 AI 协同研发范式

### 一句话定位

入职首周独立交付部署 Trace 与分析体系，并在高频迭代中反思 Spec-Driven 局限，沉淀出高效的实用型人机协作闭环。

### 30 秒版

这是我入职流舟第一周独立接手并交付的核心业务需求，打通了从对话侧生成、Trace ID 链路追踪、Token 消耗统计到部署分析页的端到端体系。面对陌生的复杂工程，我深入实践了 AI 协同开发：初期踩坑过 Spec-Driven 模式，发现其文档易过时、信息冗余以及“文档即交付”的虚假安全感；随后我调整并沉淀了实用型四步闭环：80% 方案边界对齐、定义验收标准并配备工具、大任务拆分子会话、自主编码小步验证，让 AI 真正深入工业级复杂业务交付。

### 90 秒展开版

**业务交付背景**：流舟编程部署 Trace 与分析体系是连接用户交互与后端运行时状态的核心观察窗口。用户在对话侧生成代码后，系统需生成全局 Trace ID，记录端到端 Token 消耗与输入输出，并在部署分析页呈现真实活跃、留存以及 Agent 运行结果。我入职第一周在没有完整文档的情况下独立承接，并按时高标准上线交付。

**对 Spec-Driven 开发模式的深度反思**：

刚入职时，为了追求严谨，我曾尝试过社区推崇的 Spec-Driven（规格驱动）模式——先让 AI 生成详尽的 Proposal、Design 和上千行 Tasks，逐行审阅通过后再编码。但在高频敏捷的业务实战中，很快碰壁并发现了三个致命局限：

1. **Spec 极易过时产生负向干扰**：业务需求在变、团队同事每天高频合入代码，长篇文档写完即与代码库主干产生偏差，过时的 Spec 反而给 Agent 提供了错误的上下文幻觉；
2. **文档冗余低效，审查成本高昂**：动辄上千行的文档往往信息密度极低，人工逐行 Review 耗费的时间甚至超过了直接写代码的时间，成为效率瓶颈；
3. **产生“文档即交付”的心理错觉**：在文档里推演得再完美的接口参数和组件设计，到了运行时往往会因为真实环境下的网络竞态、Token 刷新时机或样式隔离出现意外。真正的集成问题只有在运行时才能暴露。

**沉淀实用型人机协作四步闭环**：

在反思后，我将人机协同流程全面重构成轻量、可自验的实用闭环：

1. **方案与范围对齐（~80%）**：不做冗长文档，而是与 Agent 聚焦在“为什么做、边界在哪、核心架构是什么”（哪些复用已有 Package、哪些新建、状态由谁掌管）；
2. **定义验收标准并配备工具**：讲清交互流程与成功判定标准，并为 Agent 提供切换账号、Mock 数据、TrafficBridge 本地域名代理等工具，让 Agent 具备自主运行与自检的能力；
3. **大任务拆分子会话（Context 隔离）**：复杂的长链路需求按模块拆分为多个独立的 Agent 会话，主会话统筹进度与架构决策，子会话专注单模块实现，避免 Context 污染膨胀；
4. **自主编码与小步验证**：Agent 结合现有代码库与相关文档自主完成编码与自测，最后由人工进行兜底验证与微调。

### 最值得展开的技术点

- **复杂系统的快速交付能力**：首周在全新业务域独立跑通从 Trace ID 埋点、Token 统计到数据分析图表的完整业务链路。
- **对 AI 辅助研发的深刻认知**：不盲从形式主义规范，敏锐洞察到工业级开发中“过时文档”对大模型的危害。
- **“可验证性”优先于“文档详尽性”**：让人机协作的核心从“写规格”转向“构建自动化测试环境与工具基座”。

### 常见追问

**为什么你认为 Spec-Driven 在高频业务开发中难以推行？**

Spec-Driven 适合单人维护的静态小型项目，或者标准极度确定、改动周期以月计的基础设施。在云杉这种百人协同、每日数十次发布的业务仓库中，代码事实每分每秒都在变。把精力花在维护动态过时的 Markdown 文档，不如花在建设自动化测试工具、API 类型契约和快速自测环境上。

**在人机协作开发中，如何避免 AI 编写代码引入的潜在风险？**

靠两套机制防范：一是“严密的上下文约束与小步验证”，不让 AI 一次性改动十几个文件，而是限制其在单模块内渐进式编码并运行测试；二是“配备完备的验证工具”，比如账号切换工具链、本地 TrafficBridge 代理等，要求 AI 必须提供运行成功的确凿证据，最后由人工进行架构和安全兜底。

## 三、云杉科技·StreamHub 商业化实习

## 6. SIM 编辑态大表格性能优化

### 一句话定位

通过重新设计表单状态与更新粒度，把约 1400 个编辑单元格的查看态到编辑态耗时从 10 秒降到 1.8 秒。

### 30 秒版

我在 StreamHub 商业化 CRM 团队优化过一个销售业绩核算表格。查看态约 1000 个单元格，编辑态约 1400 个，切换编辑时耗时超过 10 秒。我先通过性能分析和移除实验定位到每个单元格的 `Form.Item` 注册与全量渲染是主要瓶颈；去掉 Form 后虽然降到约 5 秒，但 Context 更新仍会让所有单元格刷新并造成输入延迟。最后我用 ref 保存草稿值、发布订阅只通知受影响单元格，再结合每页 25 行、懒加载和选项按需加载，把线上交互到下一帧可见的耗时降到 1.8 秒，提速约 82%。

### 90 秒展开版

这个表格服务于季度销售业绩核算。查看态是 79 行乘 12 列的树形表格，约 1000 个单元格；编辑态展开到 79 行乘 18 列，约 1400 个单元格，并且存在校验和字段联动。原方案为了开发效率，在每个编辑单元格里使用类似 Ant Design 的 `Form.Item`。点击编辑后，表单注册、组件渲染和自定义 column render 同时发生，线上从点击到下一帧可见超过 10 秒。

我先用 Performance、React DevTools 和对照实验定位问题：删除业务 column render 或 `Form.Item` 后耗时显著下降，证明瓶颈不是接口，而是同步渲染。第一步去掉 Form，耗时降到约 5 秒，但我最初用 Context 管理数据和更新函数，一个字段变化仍会让全部消费者重新渲染，`memo` 也绕不过 Context value 变化，还出现接近 1 秒的输入延迟。

最终我把数据和视图更新拆开：ref 保存整张表的草稿值，更新函数保持稳定；每个单元格按字段订阅事件，输入时只写 ref 并通知自己或确实被联动影响的单元格。提交时再一次性读取草稿并校验。之后又增加每页 25 行、懒加载占位输入框、options 按需加载和 loading 状态，最终把同一线上埋点口径从 10 秒降到 1.8 秒。

### 最值得展开的技术点

- 用删除/替换实验定位 `Form.Item` 和自定义 render，而不是只凭感觉判断“大量 DOM”。
- ref 存数据不触发 React 更新，发布订阅把更新粒度从整表收敛到单元格。
- 联动不是取消，而是由依赖关系精确通知受影响字段。
- 分页和懒加载减少首批挂载量，状态模型优化减少后续交互重渲染，两者解决不同阶段。

### 常见追问

**为什么 `React.memo` 没解决？**

单元格直接消费了会变化的 Context，只要 Provider value 改变，消费者就会重新渲染，`memo` 不能拦住 Context 更新。发布订阅让组件只订阅自己的字段事件，才真正缩小更新范围。

**为什么不用虚拟列表？**

表格有树形层级、动态高度、复杂编辑组件和字段联动，直接上虚拟化的改造与回归成本较高。当前通过状态粒度、分页和懒加载已经达到 1.8 秒；如果数据规模继续增长，我会在行高和焦点行为可控后再评估行虚拟化。

**为什么不做单元格即时保存？**

业务要连续修改多项后统一保存，单格保存会增加接口开销、多人修改冲突和重复触发复算确认弹窗，反而打断操作流程。

**10 秒到 1.8 秒如何测量？**

简历里简称 INP，实际业务埋点是在点击编辑时记录 `performance.now()`，编辑态提交后通过 `requestAnimationFrame` 记录下一帧可见时间，并在线上保持同一口径对比。它是这次交互的自定义 interaction-to-next-paint 耗时，不应冒充 Web Vitals 对整页多次交互聚合后的标准 INP。

## 7. Account List 跨团队复用能力

### 一句话定位

把接近 2000 行的 Account 列表页面收敛成可配置 Widget，通过 Module Federation 提供给 触达团队 团队，支撑潜客批量选择和邮件触达。

### 30 秒版

StreamHub 商业化 CRM 的 触达团队 团队需要复用 Account 列表，批量选择潜客后发送邮件等操作。直接复制原页面会导致两套数据和交互逻辑长期分叉，所以我把核心 List 封装成稳定 Widget，通过 Module Federation 暴露 `AccountMyBoBList`；同时提供列与筛选项显隐、行操作开关、批量操作插槽和选中行回调。这样二方可以按场景裁剪 UI，但仍复用同一份列表逻辑和数据口径。

### 90 秒展开版

这个需求的业务背景是，销售会把潜在客户加入 触达团队，再按既定步骤发送邮件或跟进。原流程缺少批量能力，需要逐个处理；触达团队 团队因此希望直接复用 Account 列表，完成筛选、勾选和批量触达。

难点在于原页面接近 2000 行，还依赖大量样式、配置和业务逻辑。如果二方复制代码，短期看交付快，长期却会形成两套筛选、列配置和交互实现，数据口径也容易漂移。我没有直接搬页面，而是在 Widget 层增加稳定包装，将原列表作为核心实现复用，再通过 Module Federation 暴露远程模块。

为了让同一组件适配不同场景，我把差异收敛成明确接口：列和筛选项使用白名单控制，摘要、创建按钮、行操作等区域可以独立显隐；批量操作区提供 React 插槽，二方可以注入自己的按钮；列表选中数据通过回调传出，用于发送邮件等后续动作。最终二方无需维护列表副本，也能按自己的业务界面组合能力。

### 最值得展开的技术点

- Module Federation 解决运行时模块复用，Widget 接口才真正定义跨团队边界。
- 配置项控制稳定差异，插槽承载开放扩展，避免给每个业务动作增加专用布尔参数。
- 选中行通过明确回调输出，列表只负责选择，不反向依赖 触达团队 的邮件业务。
- 复用同一核心列表，避免筛选、列配置与数据逻辑形成两套实现。

### 常见追问

**为什么不直接抽成 npm 组件包？**

原页面体量大，并依赖同一应用内的样式、配置和业务模块；立即下沉为通用包会扩大改造范围。Module Federation 允许先在原应用边界内复用成熟实现，再通过稳定 Widget API 隔离二方，是交付速度和长期边界之间更合适的取舍。

**怎么避免配置项越来越多？**

把差异分三类：稳定的显隐和白名单用配置；开放的业务操作用插槽；跨边界的数据用回调。新增需求先判断属于哪一类，不为每个具体按钮追加定制接口。

**这个项目的重点是 Module Federation 吗？**

不是。MF 只是传递模块的手段，真正的难点是识别哪些逻辑必须保持单一来源、哪些 UI 可以由二方配置，以及如何让列表与批量触达业务解耦。

### 补充案例：Starling 常量文案初始化时序

一个国际化问题表现为 Starling 已经加载了正确翻译，但页面仍展示代码中的兜底文案。根因是文件顶部常量在模块 import 时立即求值，当时 Starling 尚未初始化，之后即使翻译资源就绪，常量也不会重新计算。我给出两层修复：把依赖国际化的常量改成调用时求值的方法；应用入口先等待 `initStarling`，再动态 import 主业务模块，从模块执行顺序上消除竞态。这个案例适合用来说明 ESM 模块求值时机和异步初始化边界。

## 四、远帆软件实习

## 8. qiankun 微前端基础设施与 Vite 子应用兼容

### 一句话定位

解决 qiankun 基于传统脚本执行模型与 Vite ESM 开发模式之间的冲突，并统一主子应用路由和静态资源基址。

### 30 秒版

我在远帆软件推动前端工程接入 qiankun，其中最大的难点是 Vite 子应用兼容。qiankun 的 `import-html-entry` 会把脚本放进沙箱用普通 script/eval 执行，而 Vite dev 保留 ESM 的 import/export，二者会直接冲突。单纯把生产包改成 UMD 只能解决生产集成，还会影响 code splitting，也解决不了运行时 public path。最后我用 `vite-plugin-qiankun` 适配生命周期与加载方式，并分别用 `server.origin` 和 `base` 处理开发、生产资源路径，配合主子路由同步和图片资源处理，实现多技术栈应用统一接入。

### 90 秒展开版

项目要把不同技术栈的前端应用统一挂到一个基座里。Webpack 子应用相对成熟，但 Vite 在开发环境是原生 ESM：源文件里的 import/export 不会被转成普通脚本。qiankun 的 `import-html-entry` 会抓取子应用资源，再在代理 window 的 eval 环境中执行；这个环境不是 `type=module`，所以会出现语法错误。

我先评估过 UMD 方案。它能让 qiankun 拿到 bootstrap、mount、unmount 生命周期，但只覆盖生产构建；Vite 的 UMD/IIFE 又不支持 code splitting，路由懒加载会受影响，而且 Vite 没有 Webpack 那种运行时 `publicPath`，多环境静态资源路径仍然不稳定。因此最终采用 `vite-plugin-qiankun` 把 Vite 子应用接入 qiankun 生命周期，并保持开发模式可用。

第二个问题是静态资源寻址。子应用里的图片如果按主应用 Origin 解析，就会请求到错误端口。我用 `server.origin` 解决开发环境资源来源，用 `base` 解决生产部署前缀；对于开发阶段仍难以稳定寻址的图片，我还写过 Vite 插件转成 base64 作为针对性处理。同时补齐主子应用路由同步和卸载清理，最终让不同框架的应用能够按同一规范接入。

### 常见追问

**为什么不用 UMD 作为最终方案？**

它只能覆盖生产构建，开发态仍不兼容；同时会牺牲 code splitting，且没有解决 Vite 运行时 public path。它是验证方向的过渡方案，不是完整基础设施。

`**server.origin` 和 `base` 分别解决什么？**

`server.origin` 告诉开发服务器生成的资源 URL 应使用哪个 Origin；`base` 决定生产构建产物的基础路径。两者对应不同阶段，不能互相替代。

**这段经历还缺什么量化证据？**

目前可确认的是完成多技术栈统一接入，但没有找到可靠的“接入多少个应用、节省多少时间”数据。面试前如果能补出真实应用数或迁移周期，会明显增强结果部分；没有证据时不要临时编数字。

## 五、开源项目

## 9. Agent Snapshots：Codex / Claude Code 本地会话知识库

### 一句话定位

把散落在本机 JSONL 日志里的 Agent 会话变成可浏览、可检索、可脱敏分享、并能回到原 Session 继续工作的个人知识库。

### 30 秒版

Agent Snapshots 是我做的 Codex 和 Claude Code 本地会话知识库。它通过 `agent-session-core` 把两类日志解析成统一时间线，再提供全文和本地语义检索、风险检测与自动脱敏、HTML/Markdown 导出，以及一键回到对应 Session 继续工作。语义检索使用本地 Ollama embedding 和余弦相似度，不需要把会话上传云端；续接时根据会话 ID 和工作目录调用 `codex resume` 或 `claude --resume`。我把解析能力抽成零运行时依赖的独立库，并让 Open Token Board 复用，避免展示和用量统计各写一套解析器后口径漂移。

### 90 秒展开版

我长期使用 Codex 和 Claude Code 后发现，本地积累了很多有价值的调试和实现过程，但原始会话是分散的 JSONL：很难按项目浏览，也很难搜索一句只记得大意的内容；直接分享原始日志又会泄露 token、Cookie、内网域名和本机路径。

我先把最底层的解析抽成 `agent-session-core`。它发现 Codex 与 Claude Code 的会话目录，把 message、tool call、tool result、token usage、compaction 等事件归一成统一时间线，并把 Codex 累计 token 快照转换为可处理 reset 的增量。核心库没有运行时依赖，查看器和 Open Token Board 都消费同一份领域模型。

上层查看器支持全文和语义搜索。语义搜索把会话按 chunk 建本地索引，用 Ollama 生成 embedding，再按 cosine similarity 找最相关片段；索引按会话 fingerprint 增量更新。分享前，检测和脱敏使用同一份规则表，覆盖私钥、JWT、GitHub/OpenAI key、Bearer token、连接串、Cookie 和 home 路径，避免“风险提示发现了，但导出没有真正替换”的规则漂移。

另一个差异点是会话续接。用户点击历史会话后，系统校验 UUID 和工作目录；如果对应终端已经运行就切过去，否则在正确目录执行 `codex resume <id>` 或 `claude --resume <id>`。所以它不只是只读归档，也把历史知识重新接回工作流。

### 常见追问

**全文搜索和语义搜索有什么区别？**

全文搜索适合记得准确关键词；语义搜索适合只记得问题大意。后者使用本地 embedding，把 query 和会话 chunk 映射到向量后计算余弦相似度，代价是需要本地 Ollama 和索引更新。

**自动脱敏是否绝对安全？**

不是。规则会偏向过度脱敏，并且检测与替换共用一个规则源；但任何规则都可能漏掉新格式，因此产品默认本地、只读，只有用户主动导出或分享才上传，并提醒发布前人工复核。

**“一键回到 Session”怎么实现？**

保存归一后的 engine、session ID 和 cwd。Codex 用 `codex resume`，Claude Code 用 `claude --resume`；先校验 UUID 和目录，优先切换已存在的对应终端，否则创建新终端。面试口述不需要提具体终端产品名。

**Gist 导出是什么意思？**

它是把脱敏后的静态 HTML 发布到 GitHub secret Gist，再生成可访问链接。secret Gist 不出现在公开搜索里，但拿到链接的人仍能访问，所以它不是权限系统，仍要先脱敏和人工复核。当前简历没有写这一点，只有面试官追问分享方式时再补充。

## 10. Open Token Board：AI 编码用量与额度平台

### 一句话定位

从 Codex 和 Claude Code 的本地日志采集可信用量与订阅额度，并把它们变成可对账的排行榜、趋势、额度预测和团队协作平台战报。

### 30 秒版

Open Token Board 是我做的自托管 AI 编码用量与额度平台。`token-board-agent` 在本机只读采集 Codex 和 Claude Code 日志，通过 `agent-session-core` 归一 token 事件，再上传到 Node API 和 PostgreSQL。普通同步靠稳定事件 ID 与数据库主键幂等；全量替换采用 `start / append / commit` 分阶段暂存，只有事件数和 digest 都一致时才在数据库事务中替换旧历史。上层提供排行榜、代码产出、Codex/Claude Code 额度 burn rate 和预计耗尽时间，并在额度过低时通过团队协作平台日报或周报预警。

### 90 秒展开版

这个项目最初是想做一个朋友间的 AI 编码排行榜，但很快发现真正困难的不是页面，而是数字可信。Codex 和 Claude Code 的日志目录、字段和累计/增量语义不同；同一文件可能出现在多个 home 或归档目录；Agent 每隔几分钟同步一次，网络重试也不能重复计数。

我的架构是本机 agent、API、PostgreSQL 和 Web 四层。agent 只读本地日志，按 inode 去重物理文件，通过 `agent-session-core` 把累计 token 快照转成增量事件，再做项目 basename、会话标题和 session ID 清洗。默认不上报 prompt、回复、文件内容、完整路径和密钥。服务端不信任客户端自报身份，并再次做字段和隐私校验。

普通同步用本地 checkpoint 减少上传量，但真正的一致性底座是稳定事件 ID 和 PostgreSQL 主键，网络超时可以安全重试。全量替换更危险，所以我设计成两层原子性：网络层先 `start` 声明 expected count 和 manifest digest，`append` 分批暂存，`commit` 校验完整性；数据库层再在一个事务里删除该用户旧数据并插入新数据。任何阶段失败都不动旧历史。

额度和用量也分开建模。用量回答“消耗了多少”；额度快照回答“5 小时或周窗口还剩多少”。Codex 从本地日志读取，Claude Code 通过 statusline capture 保存快照。系统根据剩余比例、重置时间和 burn rate 预测是否会提前耗尽，并把排行榜变化、PB、徽章和低额度预警发送到团队协作平台。

### 最值得展开的技术点

- 统一事件模型：同一份事实同时支持 token 排名、费用估算、趋势和个人画像。
- 两层幂等：checkpoint 只优化性能，稳定事件 ID 和数据库主键保证正确性。
- 两层原子性：上传 staging 保证数据到齐，数据库 transaction 保证正式切换完整。
- 用量和额度分离：token 总量不能直接推出订阅窗口剩余。

### 常见追问

**为什么 `start / append / commit` 还不够，还要数据库事务？**

staging 解决网络上传期间的数据完整性；事务解决正式数据从旧版本切到新版本时的原子性。只有前者，提交时数据库仍可能写一半；只有后者，数据没传完整前无法安全开始替换。

**怎么避免同一会话重复统计？**

发现阶段按设备号和 inode 去重同一物理文件；解析后生成稳定事件键；服务端以事件 ID 为主键并 `ON CONFLICT`。三层分别解决文件镜像、重复扫描和网络重试。

**token 口径怎么解释？**

排行榜的消费量使用输入加输出，不把缓存字段再重复相加；费用估算则把普通输入、缓存写、缓存读和输出按不同价格投影。Codex 的累计快照先转成相邻增量，遇到 compaction/reset 时按 reset-aware 规则处理。

**为什么正式部署用 PostgreSQL？**

早期 JSON 存储适合验证语义，但数据增长后 Node 全量读取和聚合会拖慢榜单。PostgreSQL 可以按时间范围过滤、分组和聚合，并通过事务与索引提供更稳定的一致性和查询性能；JSON 只保留为轻量兜底。

## 七、可作为备选的个人项目

## Chrome 接口 Mock 插件

### 30 秒版

我做过一个供实验室前端使用的 Chrome MV3 接口 Mock 插件。它把规则和响应数据存进 IndexedDB，在页面上下文中代理 `window.fetch` 和 `XMLHttpRequest`，匹配规则时直接返回 Mock Response，不匹配则透传真实请求。早期尝试过 `webRequest.onBeforeRequest` 重定向，但它无法直接修改响应体，Data URL 和动态 JSON 也有能力边界；后来改为页面脚本代理，同时通过外部 `injected.js` 和 `web_accessible_resources` 避免 CSP 阻止内联脚本。项目让前端可以不改业务代码、也不等待后端接口就开始联调。

### 可追问点

- content script 与页面 JavaScript 是不同执行世界，重写页面的 `window.fetch` 需要注入页面上下文。
- MV3 CSP 会阻止动态内联脚本，改成独立资源并在 manifest 中声明。
- IndexedDB 适合异步保存较大的结构化 Mock 配置，优于同步、容量更小的 localStorage。

## 九、面试表达上的最后提醒

1. **ProfilePilot 不要讲成“我做了一个自动化工具”**：突出评测 6 款市面工具后发现人机抢占焦点的业界空白，重点讲 Gateway 租约与 controlGeneration 控制代次、事务化登录态同步（diff → staging → rename），以及 DOM 悬浮条与 macOS 原生 Input Guard 分层防护。
2. **测试账号切换工具要突出“三代演进的架构思考”**：不要只说“自动登录”，重点讲一代 Playwright 模拟易脆、二代接口遇反爬签名与短信验证，三代跳出思维定式用服务端 UID 换发 Session 注入与团队协作平台 SSO `prompt=none` 静默授权，以及企业云 + AccessGate 双重鉴权。
3. **流舟 3.0 权益要强调“Headless 无头架构与业务抽象”**：突出业务逻辑与 UI 彻底解耦（Space/Coding/移动端三端复用），重点讲向上差额套餐推导（兼容老套餐与新套餐）、47 条规则树收口与 Mock 规则集沉淀，区分好个人领域抽象与团队公共 UI。
4. **商业化重构不要把 900+ 说成新写文件数**：主动亮出 518 个逻辑变更与 904 条物理新旧路径双口径；重点讲依赖方向倒置治理、Entry 显式暴露 88 个 API 彻底杜绝 `export *`，以及 ESLint 卡口防止退化。
5. **人机协同研发（AI Native）要体现“深度思考与反思”**：结合部署 Trace 交付，讲清为什么工业级开发中形式主义的 Spec-Driven 会失效（过时文档危害大、虚假交付感），展现“80% 边界对齐 + 验收标准与工具链 + 子会话隔离 + 小步自测”的实用工程闭环。
6. **StreamHub 性能优化按“定位—失败方案—粒度重构—数据结果”讲**：这是最经典、最扎实的前端性能故事，把状态下沉与精准通知讲透。
7. **开源项目只挑一个核心难点展开**：Agent Snapshots 讲会话解析/脱敏/续接；Open Token Board 讲事件幂等、PostgreSQL 聚合与额度预警。
