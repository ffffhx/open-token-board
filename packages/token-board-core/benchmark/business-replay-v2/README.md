# 真实业务历史重放与难度校验

这版用于检验题目是否能反映实际工作，以及评分是否合理。上一版两道代码小题的核心业务均为八模型全部通过，不能据此判断哪个模型更适合复杂工作；原有输入和结果保留在 [business-pilot-v1](../business-pilot-v1/README.md)。

本次采用三个有历史证据的场景。提供的是故障发生时的代码或文档材料，不是当前项目；模型自行定位原因。题包中的参考修复、历史后续答案和验收器不进入参评工作区。

首轮 [两个模型、六次独立试验的校验报告](calibration/pilot-1/README.md) 已完成：三次完整通过，另三次分别暴露读取延迟、修复遗漏和事实依据问题。报告同时保留编码影响、性能波动及首次提交证据，不能直接推导模型排名。

补充 [GPT-6.1 Sol、GPT-6 Sol、GPT-6 Luna 的九次试验报告](calibration/pilot-2/README.md) 已完成，七次完整通过。三款模型均通过性能与 Profile 题；文档题分别出现分隔线遗漏和未恢复开场，两种失败的程度不同。补测统一在初始消息提供题面并明确 UTF-8 读取，与首轮输入呈现方式有差异，不能当作完全相同条件的重复试验。

## 评分与校验

业务、保全、交付和格式精度分别记录。业务通过要求请求的行为成立且受保护数据或内容未受损；交付另查说明是否可读、证据是否真实。末尾空行等格式差异单列，不单独替代业务判定。自然语言的事实和可读性由协调 Agent 按来源复核，明确标记为 Agent 复核，不冒充人工评审。

先验证历史基线会在指定业务项失败、参考修复通过，再验证不完整或破坏性修复会失败、合理替代实现可以通过。B09 还使用 [逐项事实复核规则](cases/B09/fact-rubric.json)：数字规则仅触发非阻断的审查提示，由语境与来源判断是否虚构。其「虚构成果」负向对照必须在正式事实复核中失败；后置否定的合理表述则可通过，两者见 [对照复核](cases/B09/control-review.json)。机器通过不等于完整验收通过。题目不会为了压低通过率而事后修改。

冻结清单同时记录全部题目材料、验收器和统一 runner 的哈希。冻结后任何评分或输入变化都需要新版本。提交只验收第一次结果，协调者不修参评代码，不向参评者回传隐藏验收结果。

## 小样本执行协议

[suite.json](suite.json) 预先约定 GPT-6 Astra 与 GPT-5.6 Luna 各跑三题，共六次；统一 medium，每题全新上下文，单次 45 分钟上限。依赖预装不计入模型时间，记录实际会话配置、用时和 Token；无账单数据时费用留空。B02 性能执行串行，避免其他评测任务竞争资源。

这六次仅用于难度与评分校验，不产生模型排名、稳定成功率或个人模型推荐。独立导出与读取范围由指令约束，没有操作系统级隔离；不声称能防范恶意参评程序。

后续三模型补测遵循独立冻结的 [pilot-2 协议](calibration/pilot-2/protocol.json)，仍为每题一次、medium、全新上下文、45 分钟上限；原题包和验收器保持不变。每次允许提交前自行修改与自测，提交后不回传隐藏分数或补改答案。

## 运行方式

从仓库根目录运行。B04 需要按其 `task.json` 准备固定版本浏览器并设置 `PLAYWRIGHT_BROWSERS_PATH`；B02 的准备脚本负责独立运行环境。准备失败属于环境问题，候选语法或业务失败属于提交结果。

```powershell
node tools/eval-runner/business-replay.mjs validate
node tools/eval-runner/business-replay.mjs freeze
node tools/eval-runner/business-replay.mjs check
node tools/eval-runner/business-replay.mjs prepare B04 --out <新的独立目录>
node tools/eval-runner/business-replay.mjs grade B04 --workspace <独立目录> --report <报告文件>
```

`freeze` 只运行一次，已有清单不能覆盖。`prepare` 只导出参评输入、题面及运行所需依赖。`grade` 记录自动验收和修改范围，事实复核仍需完成。验证报告与模型结果必须区分，参考修复通过不计为模型通过。
