# 榜单完整快照刷新

本地服务：http://127.0.0.1:58010/api/usage/leaderboard?range=today&metric=tokens （`pnpm dev`，当前会话保持运行）。服务使用 replay 创建的独立 PostgreSQL 和 3,905 条合成事件；冻结业务时间为 `2026-09-14T12:00:00.000Z`，业务日按 Asia/Shanghai。

## 定位与修改

基线 `pnpm measure` 的七轮外部刷新耗时为 7.05–8.15 秒，API 进程每轮消耗约 6.4–8.0 秒 CPU 时间。源码中的刷新循环按九种范围、六种指标依次调用 PostgreSQL 统计函数；同一范围的六种指标重复执行相同的用户、日、模型、工具、历史、荣誉和事件查询，虽然指标仅改变排名。此次保留原 PostgreSQL 统计函数和全部字段，在一次完整刷新内部按 SQL 文本与参数复用只读查询结果；刷新结束即丢弃复用表，后续刷新会重新读取历史修正。每项计算后让出事件循环，使 HTTP 读取有机会继续使用上次已提交的快照。若任一查询失败，构建中止，原有快照映射保持有效；原有重叠刷新共用同一个刷新 Promise。

没有减少范围或指标，也没有替换原有费用、排序、上期变化、荣誉、效率、趋势、团队、项目、分布和逐日等计算。`artifacts/baseline.json` 与 `artifacts/candidate.json` 中的 54 个完整快照逐字段深比较相等，包括记录数和所有 summary 内容。

## 实测

命令：先运行 `pnpm measure` 并保存 `artifacts/baseline.json`；修改后运行 `pnpm typecheck`、`pnpm measure`，保存 `artifacts/candidate.json`；再运行 `node --import tsx tests/replay/verify.mjs` 和 `pnpm dev`。两次测量都由 `replay/run.mjs` 启动新隔离 PostgreSQL、写入相同确定性合成数据、预热一次，然后对七次完整刷新进行外部计时，同时发起 HTTP 快照读取。原始逐轮 HTTP 延迟与 API CPU/RSS 保存在上述 JSON；进程其他资源指标见各自运行目录。

本地基线与候选是先后测得，并非验收所述交替七轮；本记录不能代替独立交替重放。HTTP P95 仅代表此合成数据和本机负载。CPU/RSS 指 API 进程，不包含 PostgreSQL 进程。
