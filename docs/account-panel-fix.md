# “我的 Token 消耗”加载修复（2026-09-15）

`GET /api/usage/me` 是登录后的个人面板接口，与此前优化的公开资料 `/api/usage/user` 不同。它仍然读取当前用户全部历史，并在 HTTP 主进程中重复生成榜单与成就。现场账号有约 41.2 万条记录，最近 24 小时只有约 500 条；截图时 API 容器占用约 2.27 GiB 内存。前端请求没有超时，因此等待期间一直显示骨架屏。

修复复用榜单快照中的排名和历史成就，通过 `(user_id, reported_at)` 索引读取所选范围。目标进度使用上海时区的每日 SQL 汇总，保留旧数据缺失费用时的估价逻辑。个人计算移到独立进程，限制队列并在 60 秒后结束超时计算。窗口内无排名的账号仍读取历史以保留已有成就；较大范围的首次计算仍可能比日视图慢。

前端增加 65 秒请求超时、切换范围时取消旧请求和失败重试按钮。这部分已在本地构建，尚未发布到 GitHub Pages；线上面板恢复依赖本次已部署的后端修复。

## 验证

- PostgreSQL 对照：9 种时间范围的完整个人结果与原算法一致，包括排名、明细、成就、热力图和目标进度；覆盖没有近期数据的账号、空账号和旧记录费用估算。
- 独立进程超时测试通过；真实 PostgreSQL 的 HTTP 测试验证匿名请求返回 401，登录请求返回 200，查询参数不能改变当前账号。
- Core、API、Web 类型检查及 Web 构建通过；本地 `http://localhost:3001/board/` 返回 200。
- 完整 API 测试第一次运行 67 项，其中 66 通过、1 失败：未修改的 `tests/api/asc-collector.test.ts` 扫描测试得到 804，预期 805。单独重跑也失败，该项尚未解决。

## 生产数据测量

在只读、0.75 CPU、1100 MiB 容器 / 768 MiB Node 堆限制下，修复版读取 509 条记录，计算耗时 342 ms，进程峰值 RSS 178 MiB。相同限制下，旧算法读取约 41.2 万条后，在约 71 秒发生堆内存不足，未完成。因此不据此宣称旧生产请求的精确耗时或加速倍数。

生产容器内的完整独立进程调用耗时 689 ms，返回 520 条记录、50,292,468 tokens、13 个会话；同期 10 次普通榜单请求中位数 13 ms、最大 91 ms。两次测量间有正常上报，因此记录数不同。这是共享服务器上的单次检查，不是压力测试。
